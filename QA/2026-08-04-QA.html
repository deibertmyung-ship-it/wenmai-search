二、文档格式与解析器

项目目前支持解析哪些文档格式？

解析器主要格式说明
内置 TextParser txt、md、markdown、text、rst、log、csv 直接解析，不需要模型或外部服务
Docling pdf、docx、pptx、xlsx、html、图片等 默认富文档解析器
Unstructured doc、ppt、xls、epub、eml、msg、rtf、odt，以及常见 PDF/Office/图片 Docling 失败时的通用降级解析器
Marker pdf 面向 PDF 的高质量兜底解析器

默认解析链为：docling → unstructured → marker；纯文本输入始终优先使用内置解析器。

部署时是否会自动安装 Docling、Unstructured、Marker？

已将三者从可选依赖调整为后端核心依赖。标准 Python 安装和 Docker 镜像构建都会安装三种解析器；Docker 还会安装 libmagic、Poppler、Tesseract 等常见 PDF/OCR 系统组件，并在构建阶段校验项目实际使用的 import 路径。

Marker 当前固定在兼容现有适配器的 1.x 版本，避免 2.x 公共 API 变化导致运行时错误。

安装三个解析库后，还需要配置相关 API 吗？

不需要。当前实现中三者都在本机进程内解析：

  • Docling 使用本地 DocumentConverter。
  • Unstructured 使用本地 partition。
  • Marker 使用本地模型推理。

部分 PDF/OCR 首次解析可能下载模型权重，因此需要允许首次联网或预先准备模型缓存，但这不是解析 API，也不需要 API Key。

三、Word 上传与后台任务

为什么上传 Word 后任务一直未完成？

诊断时发现两个独立问题：

  1. 任务状态为 pending、尝试次数为 0，说明没有 worker 领取任务。
  2. 当时环境没有安装 Docling、Unstructured 或 Marker；即使 worker 启动，DOCX 解析也会因缺少依赖失败。

处理后，文档“承载网规划管理岗位知识点汇编.docx”状态已变为 completed，成功生成 75 个 chunk，当前版本已写入索引。

为什么上传后不自动解析，还要手动运行 run.bat worker？

问题发生时，本地工作流把“登记任务”和“执行任务”分开：

Web 上传 → 文件落盘 → 创建 pending 任务 → worker 解析/切分/嵌入/索引

旧版 run.bat 只启动 API 和 Web，不启动常驻 worker。安装解析库只能保证 worker 能解析文件，不能自动启动 worker。

另外，旧版本地使用嵌入式 Qdrant，同一数据目录不能由独立 API 与 worker 进程同时占用。因此 run.bat worker 会暂时停止 API、排空队列，然后恢复 API。

该限制现已解决：本地仍使用嵌入式 Qdrant，但 worker 改为 API 进程内的常驻线程，与请求线程共享同一个 Qdrant 客户端。

正式部署后也需要手工运行 worker 吗？

不需要。完整 server profile 使用独立常驻 worker；Windows local profile 由 API 生命周期 自动启动内置 worker。run.bat worker 仅作为兼容命令重启整个本地栈。

四、Qdrant 基础

Qdrant 是什么？

Qdrant 是一个向量数据库，用于保存文档向量并查找语义最相近的内容。它不负责解析 Word，也不负责生成最终回答。

文档 → 解析文字 → 切分 chunk → 嵌入模型生成向量 → Qdrant 保存并检索

例如用户搜索“光缆一公里有多少延迟”，即使原文写的是“光纤传输 1km 的时延约为 5μs”，向量检索仍有机会根据语义相似度找到它。

“本地使用嵌入式 Qdrant”是什么模式？

“嵌入式”表示 Qdrant 不作为独立服务运行，而是由 Python 直接打开本地目录：

QdrantClient(path=".kbdata/qdrant")
模式优点限制
嵌入式 Qdrant无需 Docker、端口和独立服务本地目录有进程独占限制
Qdrant ServerAPI 与多个 worker 可同时连接需要运行服务或容器

这里的“嵌入式”是部署方式，不是“文本嵌入模型”。当前项目本地默认使用该模式，数据位于 .kbdata/qdrant；server profile 才使用独立 Qdrant Server。

什么是 Sparse 检索？

Sparse（稀疏）检索主要依据关键词、字符或词项是否匹配。本项目使用字符 1-gram / 2-gram 与 BM25，特别适合中文专有名词、设备编号、标准号和原文措辞。

检索方式判断依据擅长场景
Sparse / BM25关键词和字符匹配G.655、PTN7900、5μs/km 等精确内容
Dense / 向量语义相似度查询与原文说法不同但意思相近

项目将两路结果通过 RRF 融合：Dense 负责“意思像不像”，Sparse 负责“关键词对不对”。

本地切换到独立 Qdrant Server 和常驻 worker，工程量和依赖大吗？为什么最初没有默认这样设计？

核心后端原本就支持 KB_QDRANT_URL 和常驻 kbsvc worker，所以改造量主要在本地编排、进程管理、健康检查、日志和旧索引迁移，属于小到中等工程。

无需新增 Python 依赖；需要 Docker Desktop（或 Docker Engine）运行 Qdrant Server。最初选择嵌入式模式，是为了做到不安装 Docker 即可演示，但牺牲了 API 与 worker 并行运行能力。

曾完成独立 Qdrant Server 方案，但评估 Docker 依赖后，最终本地方案调整为：

SQLite + 本地文件存储 + 嵌入式 Qdrant + API 内置 worker
  • run.bat 只启动 API 与 Web，不需要 Docker。
  • 上传任务自动处理，不再要求手动排空队列。
  • API 请求与 worker 线程共享进程级 Qdrant 单例，并串行化嵌入式读写。
  • 需要多 API 或多 worker 时，再切换完整 server profile。

为什么独立 Qdrant 方案需要 Docker？没有 Docker 能否实现？

Qdrant 本身不强制依赖 Docker；Docker 只是负责稳定运行独立服务、固定版本、映射端口和保存数据卷。也可以使用原生 Qdrant、WSL、Podman 或远程 Qdrant。

对于本项目的单机使用场景，最终选择更轻量的无 Docker 方案：将 worker 放进 API 进程，使它和请求线程共享嵌入式 Qdrant。代价是本地只能运行一个 API 进程、不能水平扩展 worker。

五、嵌入模型与自定义

本项目实际使用哪个嵌入模型？

通过 run.bat 启动时，当前实际配置为：

  • Provider：fastembed
  • 模型：BAAI/bge-small-zh-v1.5
  • 向量维度：模型自动检测为 512
  • Sparse 检索：字符级 BM25，不需要神经网络模型

代码的零配置兜底是 hash 384 维，它用于离线测试，不是真正的语义嵌入模型。

默认嵌入模型能否自定义？

可以。主要环境变量如下：

环境变量用途
KB_DENSE_PROVIDERfastembed、openai 或 hash
KB_DENSE_MODEL模型名称
KB_DENSE_DIM向量维度；FastEmbed 会优先探测实际维度
KB_DENSE_BATCH_SIZE嵌入批大小
KB_MODEL_CACHE_DIR本地模型缓存目录
KB_OPENAI_BASE_URLOpenAI 兼容嵌入服务地址
KB_OPENAI_API_KEYOpenAI 兼容服务密钥

本地 run.bat 会提供 FastEmbed 默认值，但尊重外部已经设置的环境变量；自定义 provider 和模型无需再修改脚本硬编码。

更换嵌入模型后，已有文档需要重新上传吗？

不需要重新上传或重新解析，但必须重新生成全部向量：

run.bat reembed

reembed 会复用已经保存的 chunk，重建 Qdrant 集合。若不重建，新旧向量语义空间不一致；维度不同时还会直接报错。

八、三种检索模式是否真的对应三条后端路径

混合 / 语义 / 字面，切换时后端真的走不同逻辑吗？

是，三条路径都是真的。但项目原有的测试证明不了这一点—— test_every_retrieval_mode_returns_results 只断言「三种模式都有结果」， 即使 mode 被完全丢弃，这个断言照样通过。所以我写了能证伪的探针，对运行中的系统实测：

检查hybriddensesparse
实际跑了哪些召回器[dense, sparse][dense][sparse]
融合权重1.0 / 1.01.0 / 0.00.0 / 1.0
计时字段两个都在只有 dense_search只有 sparse_search
候选数20 / 2020 / 00 / 20

最硬的证据：hybrid 融合前，dense 与 sparse 的 top-8 重合度 0/8—— 两路返回完全不同的候选，不可能是同一条代码路径。另外 mode=magic 返回 422，不是静默回退。

既然模式是真的，为什么界面上「混合」和「字面」经常看起来一样？

因为 lexical reranker 把混合模式拉回了字面模式。召回层确实是混合的，但默认的 KB_RERANKER=lexical 按字面重合度重排，系统性地把 sparse 候选顶上来：

查询rerank ON ∩sparsererank ON ∩densererank OFF ∩sparse
贼克如何取用神0.670.180.11
涉害深者为用1.00（完全一致）0.110.33
昴星课如何取用0.670.330.11

关掉 rerank 后 hybrid 与 sparse 只重合 0.11–0.33，说明融合是真的。不是模式没接通，是重排器把 dense 的贡献洗掉了。

九、检索调试 / 查询改写 / 重排 三个复选框

这三个开关分别做什么？功能正常吗？

三个都正常，没有装饰性开关。前端未勾选回传（靠隐藏字段 f=1 区分「没提交过」与「用户关掉了」）也验证正确。

开关作用关键实现
检索调试 只读开关，不参与检索——勾选前后结果完全一致 双重门禁：KBWEB_DEBUG_UI 控制复选框是否出现，服务端再校验一次，手工构造 ?debug=1 也拿不到
查询改写 规则式去噪，不调 LLM：去句尾标点、剥开头框架词、按标点切分多意图 原查询永远排第一，最多 3 个变体，每个变体独立跑一遍检索
重排 对超额召回的候选池二次排序：实测重排 40 个候选再取前 10，能把原本第 11–40 位的段落提到首屏 0.7×覆盖率 + 0.2×密度 + 0.1×靠前度，离线、亚毫秒

查询改写实际改了什么？

[空转] 贼克如何取用神        -> ['贼克如何取用神']
[展开] 如何取用神           -> ['如何取用神', '取用神']
[展开] 什么是涉害           -> ['什么是涉害', '涉害']

十、5.6 秒瓶颈的根因

为什么每次检索要 6 秒以上？

实测拆解：

              sparse_search    dense_search
贼克如何取用神      5632 ms         391 ms
涉害深者为用        5638 ms         399 ms
昴星课如何取用      5392 ms         383 ms

字面检索比语义慢 14 倍，占 hybrid 总耗时的 93%。按查询长度扫描后发现 约 4.9 秒是固定成本，只有 ~20ms/词是可变的。

根因不在 BM25、不在字符 n-gram、也不在 Qdrant 引擎，而在 嵌入式 qdrant-client 的 local 模式根本没有稀疏倒排索引：

# qdrant_client/local/sparse_distances.py:109-121
for vector in vectors:                        # 22,659 次纯 Python 循环
    score = sparse_dot_product(query, vector) # 内部还有 2 次 assert is_sorted 全扫

同一模式下 dense 只要 390ms，因为它走 numpy（C 实现）。qdrant_store.py:81 的注释其实早就承认了： 「Embedded Qdrant scans payloads directly」。

在换引擎之前，有哪些免费的优化？

我提出了两个，其中一个经实测是无效的，没有做。

① 多变体合并为单次扫描 —— 做了。改写的每个变体原本各跑一遍全库扫描：

查询变体数改前改后结果重合
贼克如何取用神15,587ms5,599ms1.00
什么是涉害210,571ms5,317ms1.00
解释一下昴星课以及遥克课316,356ms5,654ms1.00

延迟从「随变体数线性增长」变成常数，而且结果重合度全部 1.00——连融合前的原始召回排序都逐位一致。 原因可以证明：rewrite 只做减法，所以每个变体都是原查询的连续子串， 字符 n-gram 必然是原查询的子集，取并集就等于原查询自己。也就是说改写变体对稀疏检索本来毫无贡献，纯粹白烧 5 秒一次。

② 调低 overfetch —— 我判断错了，没有做。我原本说「local 下调到 2 能省掉一半」。实测：

top_k   limit   sparse_search_ms   rerank_ms
    1       4           5633.9         1.7
   10      40           5608.3        13.3
   25     100           5598.9        33.7

limit 变化 25 倍，扫描时间纹丝不动——因为 calculate_distance_sparse 对全部向量算完分才截断， limit 根本不进入扫描成本。调低它只会白白损失召回深度，换来 30ms。 做一个已知无效还有副作用的改动，比不做更糟。

十一、Tantivy 选型评估与实施

该引入 Tantivy 还是 Whoosh？

方案预期延迟代价
A. 跑 Qdrant server~10–50ms零代码改动，但需要 Docker，直接违背 run.bat 反复强调的核心设计目标
B. SQLite FTS5~5–20ms破坏双 profile 一致性：local 是 SQLite、server 是 Postgres，得写两套
C. Tantivy~1–5ms多一个需同步的存储；多一个编译依赖
D. Whoosh~50–200ms2016 年后停止维护；纯 Python

Whoosh 直接排除——等于为了「把 Python 全扫换成 Python 倒排」引入一个无人维护的依赖， 拿到 Tantivy 一个零头的收益。选 Tantivy：它是唯一同时满足「真索引 + 无 Docker + 双 profile 一致」的选项， 而且接缝已存在（融合、重排、引文、调试全部与召回器无关），并且它让我们删代码而不是加代码。

「支持模糊搜索」能作为立项理由吗？

不能。Tantivy 的 fuzzy_term_query 是编辑距离匹配。原型实测：

fuzzy('涉宝', distance=1) -> 返回「三井 / 壬子癸 / 天河」等完全无关内容

汉字的编辑距离没有语义含义——「涉害」和「涉宝」距离是 1 但毫无关系。而且 现有的字符 n-gram BM25 本身已经是一种模糊匹配，错一个字仍能命中大部分词项。

结论：上 Tantivy 是为了速度和删掉自研 BM25，不是为了模糊搜索。

动手前做了什么验证？

我把「tantivy-py 的中文分词能力」标为单点否决项，先用真实的 22,659 段语料做原型：

延迟（warm median）    0.23 – 1.24 ms     ← 原为 5,600 ms
建索引                13.3s / 22,659 段
删除文档              106ms

并对比排序质量（top-10 含关键词数），确认持平或略好：5/10 vs 4/10、8/10 vs 7/10、10/10 vs 10/10。 其中一条看似很差的结果（「什么是涉害」top-1 是一段现代对话），查证后发现现有系统也排在第一， 是查询里「什么」这个高频词的问题，不是 tantivy 的问题。

最终删掉了哪些代码？

  • embedding/sparse_bm25.py 整个自研 BM25（117 行）
  • db/repo.py 的词表统计维护（110 行，含方言分支 upsert 与可移植回退路径）
  • term_stat / corpus_stat 两张表 —— 统计改由索引自持，不再有漂移的可能
  • term_index() 的 crc32 % 2^31 词项哈希 —— 顺带消除静默碰撞风险
  • VectorPoint.sparse、VectorStore.search_sparse、Qdrant 稀疏向量配置

保留了 tokenize()（移至 lexical/tokenizer.py）：中英分治的字符 n-gram 切分是领域知识，Tantivy 自带的 ngram 分词器会把 hybrid 也切成字符。语料学归我们，索引与打分归引擎。

实施中卡了什么？

Windows 上批量重建必然失败（PermissionDenied on .pos / .fieldnorm）。 做了区分实验：同样的代码在 %TEMP% 下跑通，在项目目录树下三个位置全部失败—— 不是 .kbdata 特有。Defender 服务是关的，大概率有第三方安全软件在扫用户目录， 多个索引线程并发建/换段文件时与扫描器抢句柄。

没有去动安全软件。改为 KB_LEXICAL_WRITER_THREADS=1，并让批量重建走单次提交。 代价是全量重建慢约 2 倍（21 秒），增量写入零影响。

过程中还有一个我自己引入的偶发缺陷：rebuild_lexical 用了单次提交，但 reembed_tenant 里忘了包 —— 复现率约 40%。修复后连跑 8 轮零失败， 测试套件本身也从 13–23 秒降到 10 秒。

最终效果？

指标改前改后
词法检索（中位数）5,600 ms2.5 ms
三变体查询16,400 ms2.5 ms
hybrid 总耗时~12,500 ms413 ms
Qdrant 体积339.6 MB179.0 MB

Qdrant 瘦身是因为删掉稀疏向量后集合不会自动回收，必须跑一次 reembed 才兑现。 新增 kbsvc rebuild-lexical：只重建词法索引（21 秒），不重跑嵌入模型。

瓶颈已经转移到稠密一路（396ms，嵌入式 Qdrant 全量扫描无 HNSW）。语料继续增长时切 Qdrant Server 是主要手段。

十二、繁简/异体字与拼音搜索

项目支持繁简归一化和拼音搜索吗？

原本两个都不支持，而且繁简这条不是理论问题——语料本身就是混排的：

简 阴 × 44,548    繁 陰 ×   524
简 发 × 15,707    繁 發 ×   512
简 阳 × 41,610    繁 陽 ×   402

不归一化时，词法一路查 阴阳 与查 陰陽 重合 0/10，完全不相交。 dense 靠模型部分容忍，但只有 2–5/10，不能算「支持」。

拼音方面：sparse 返回 0 条（正确）；dense 对 zeike 返回 5 条，但那不是命中—— ANN 检索对任何输入都会返回 top-k 最近邻。别把它当作「支持拼音」。

为什么不用「同时索引简繁两种形式」？

试过，被数据否决：双写结果 100% 偏向繁体。

对         简  繁  双写   双写∩简   双写∩繁
阴阳/陰陽   10  10   10    0/10     10/10
发用/發用   10  10   10    0/10     10/10

原因是 BM25 的 IDF：陰 只出现 524 次、阴 出现 44,548 次， 稀有形式 IDF 高得多，直接主导打分，把常见形式挤出结果。 正确做法是折叠到单一形式——它把两边的 doc frequency 合并，而不是让它们竞争。

实现时最关键的三个约束是什么？

  1. 只作用于检索表示，绝不改写存储文本。 payload.text 是渲染 snippet 与引文的依据，改写古籍原文等于篡改。实测验证： 
    用【简体】「阴阳」检索 → 召回纯繁体的《天無陰陽篇》
snippet: 天無陰陽篇第一 經曰：天圓地方，本乎陰陽。陰陽旣形，逆之則敗…
高亮[2:4] = '陰陽'    ← 偏移精确落在繁体形上
  2. 必须长度守恒。citation.build_snippet 用 str.find 定位高亮并返回偏移量， 归一化若改变长度会让偏移静默漂移。因此自建严格 1:1 字符映射表 （4,300 条，从 zhconv 逐字提取并校验零条非 1:1），而不是整串调 convert()。 用 zh-hans 而非 zh-cn——后者会做大陆词汇替换（軟體 → 软件），改写古籍用词不是我们该做的事。
  3. 领域保护名单。zhconv 把 乾 折叠成 干（取「干燥」义）， 但查过语料上下文后发现本语料中 乾 全是卦名： 
    乾为 × 2,806    乾坤 × 2,749    乾之 × 1,089    乾卦 × 293
…仲月辰巽及乾坤。季月乙丁与辛癸…
…没四维乾坤艮巽，大吉，百事无碍…
    与巽/艮/坤同现，零个干燥义。折叠会把「乾坤」和「干支」（25,748 次）合并——两个核心且无关的概念。 已验证两者检索重合 0/10。这是查过语料才定的，不是想当然。

最终效果？

查询对词法·前词法·后稠密·前稠密·后
阴阳 / 陰陽0/1010/104/1010/10
遥克 / 遙克0/1010/104/1010/10
万 / 萬0/1010/102/1010/10

两路都做且都在单一入口：词法侧在 tokenize() 内部折叠（索引与查询共用同一函数）； 稠密侧用 FoldingDenseEmbedder 包装嵌入器——那里有 worker / reembed / pipeline 三个调用点，包装比在每处写一遍更难漏。成本可忽略：str.translate 走 C 实现，120 万字 65ms。

拼音搜索为什么建议不做？

技术上可行（pypinyin + Tantivy 加一个 body_pinyin 字段），但三个理由不划算：

  1. 同音字爆炸。liuren 会同时匹配「六壬」「流人」「留任」「柳仁」。
  2. 文言文多音字消歧不准。壬、行、重、度—— pypinyin 的消歧模型按现代汉语训练，对文言文经常判错，而错的读音会静默污染索引。
  3. 与产品定位冲突。这套系统的价值主张是「给出可核对的出处」， 拼音检索天然模糊，降低的正是它最想保证的东西。

真正的中文「模糊」需求是繁简、异体字、OCR 错字——前两类用归一化表解决更对路，也便宜得多。

十三、交付与遗留

改动如何提交？

分支 refactor/tantivy-lexical-index，三个 commit， PR #4：

e3de713  docs: 更新架构描述               10 个文件
a1104c6  feat: 繁简与旧字形归一化          8 个文件
e751920  refactor: 用 Tantivy 替换自研 BM25  27 个文件

有 7 个文件同时含两部分改动，而 git add -p 在这个环境不可用。 做法是：备份最终版 → 把这些文件回退到「只含 Tantivy 改动」的状态 → 验证通过后提交 → 还原最终版再提交。 这样每个 commit 都是能跑通的完整状态，而不是切一半的快照。

在独立 git worktree 里逐个验证：commit 1 → 119 passed，commit 2 → 128 passed。

第一次 worktree 验证失败过，是 Windows 260 字符路径上限导致的，换短路径后正常，不是提交内容的问题。

还有什么没做？

PR 的测试计划里明确标了三项未验证：

  • Linux / macOS 上验证 —— 全部实测都在 Windows 上做的
  • server profile 验证 —— 本次只测了 local profile
  • 多 worker 场景 —— Tantivy 持目录锁，server profile 下需让词法写入集中在单一写入者后面，本 PR 未处理

已知遗留三条：

  • docs/06-code-architecture.md 的复杂度与社区检测数据来自代码图谱工具， 早于本次重构且无法凭空重算。已加时效警告、重测行数、把失效条目用删除线标注， 并把「重跑图谱索引」列为最高优先级改进项。
  • reembed 中途被打断时词法索引会停在上次提交状态（单次提交的代价）。 稠密侧 --resume-after 续跑，词法侧 rebuild-lexical 重建即可。
  • 稠密检索成为新瓶颈（396ms）。

另有两处已发现但未修的小问题：调试抽屉缺少重排那一节； 查询改写的 startswith 边界导致中间出现的框架词剥不掉。
