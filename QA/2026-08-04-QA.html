二、文档格式与解析器

项目目前支持解析哪些文档格式？

解析器主要格式说明
内置 TextParser txt、md、markdown、text、rst、log、csv 直接解析，不需要模型或外部服务
Docling pdf、docx、pptx、xlsx、html、图片等 默认富文档解析器
Unstructured doc、ppt、xls、epub、eml、msg、rtf、odt，以及常见 PDF/Office/图片 Docling 失败时的通用降级解析器
Marker pdf 面向 PDF 的高质量兜底解析器

默认解析链为：docling → unstructured → marker；纯文本输入始终优先使用内置解析器。

部署时是否会自动安装 Docling、Unstructured、Marker？

已将三者从可选依赖调整为后端核心依赖。标准 Python 安装和 Docker 镜像构建都会安装三种解析器；Docker 还会安装 libmagic、Poppler、Tesseract 等常见 PDF/OCR 系统组件，并在构建阶段校验项目实际使用的 import 路径。

Marker 当前固定在兼容现有适配器的 1.x 版本，避免 2.x 公共 API 变化导致运行时错误。

安装三个解析库后，还需要配置相关 API 吗？

不需要。当前实现中三者都在本机进程内解析：

  • Docling 使用本地 DocumentConverter。
  • Unstructured 使用本地 partition。
  • Marker 使用本地模型推理。

部分 PDF/OCR 首次解析可能下载模型权重，因此需要允许首次联网或预先准备模型缓存，但这不是解析 API，也不需要 API Key。

三、Word 上传与后台任务

为什么上传 Word 后任务一直未完成？

诊断时发现两个独立问题：

  1. 任务状态为 pending、尝试次数为 0，说明没有 worker 领取任务。
  2. 当时环境没有安装 Docling、Unstructured 或 Marker；即使 worker 启动，DOCX 解析也会因缺少依赖失败。

处理后，文档“承载网规划管理岗位知识点汇编.docx”状态已变为 completed，成功生成 75 个 chunk，当前版本已写入索引。

为什么上传后不自动解析，还要手动运行 run.bat worker？

问题发生时，本地工作流把“登记任务”和“执行任务”分开：

Web 上传 → 文件落盘 → 创建 pending 任务 → worker 解析/切分/嵌入/索引

旧版 run.bat 只启动 API 和 Web，不启动常驻 worker。安装解析库只能保证 worker 能解析文件，不能自动启动 worker。

另外，旧版本地使用嵌入式 Qdrant，同一数据目录不能由独立 API 与 worker 进程同时占用。因此 run.bat worker 会暂时停止 API、排空队列，然后恢复 API。

该限制现已解决：本地仍使用嵌入式 Qdrant，但 worker 改为 API 进程内的常驻线程，与请求线程共享同一个 Qdrant 客户端。

正式部署后也需要手工运行 worker 吗？

不需要。完整 server profile 使用独立常驻 worker；Windows local profile 由 API 生命周期 自动启动内置 worker。run.bat worker 仅作为兼容命令重启整个本地栈。

四、Qdrant 基础

Qdrant 是什么？

Qdrant 是一个向量数据库，用于保存文档向量并查找语义最相近的内容。它不负责解析 Word，也不负责生成最终回答。

文档 → 解析文字 → 切分 chunk → 嵌入模型生成向量 → Qdrant 保存并检索

例如用户搜索“光缆一公里有多少延迟”，即使原文写的是“光纤传输 1km 的时延约为 5μs”，向量检索仍有机会根据语义相似度找到它。

“本地使用嵌入式 Qdrant”是什么模式？

“嵌入式”表示 Qdrant 不作为独立服务运行，而是由 Python 直接打开本地目录：

QdrantClient(path=".kbdata/qdrant")
模式优点限制
嵌入式 Qdrant无需 Docker、端口和独立服务本地目录有进程独占限制
Qdrant ServerAPI 与多个 worker 可同时连接需要运行服务或容器

这里的“嵌入式”是部署方式，不是“文本嵌入模型”。当前项目本地默认使用该模式，数据位于 .kbdata/qdrant；server profile 才使用独立 Qdrant Server。

什么是 Sparse 检索？

Sparse（稀疏）检索主要依据关键词、字符或词项是否匹配。本项目使用字符 1-gram / 2-gram 与 BM25，特别适合中文专有名词、设备编号、标准号和原文措辞。

检索方式判断依据擅长场景
Sparse / BM25关键词和字符匹配G.655、PTN7900、5μs/km 等精确内容
Dense / 向量语义相似度查询与原文说法不同但意思相近

项目将两路结果通过 RRF 融合：Dense 负责“意思像不像”，Sparse 负责“关键词对不对”。

本地切换到独立 Qdrant Server 和常驻 worker，工程量和依赖大吗？为什么最初没有默认这样设计？

核心后端原本就支持 KB_QDRANT_URL 和常驻 kbsvc worker，所以改造量主要在本地编排、进程管理、健康检查、日志和旧索引迁移，属于小到中等工程。

无需新增 Python 依赖；需要 Docker Desktop（或 Docker Engine）运行 Qdrant Server。最初选择嵌入式模式，是为了做到不安装 Docker 即可演示，但牺牲了 API 与 worker 并行运行能力。

曾完成独立 Qdrant Server 方案，但评估 Docker 依赖后，最终本地方案调整为：

SQLite + 本地文件存储 + 嵌入式 Qdrant + API 内置 worker
  • run.bat 只启动 API 与 Web，不需要 Docker。
  • 上传任务自动处理，不再要求手动排空队列。
  • API 请求与 worker 线程共享进程级 Qdrant 单例，并串行化嵌入式读写。
  • 需要多 API 或多 worker 时，再切换完整 server profile。

为什么独立 Qdrant 方案需要 Docker？没有 Docker 能否实现？

Qdrant 本身不强制依赖 Docker；Docker 只是负责稳定运行独立服务、固定版本、映射端口和保存数据卷。也可以使用原生 Qdrant、WSL、Podman 或远程 Qdrant。

对于本项目的单机使用场景，最终选择更轻量的无 Docker 方案：将 worker 放进 API 进程，使它和请求线程共享嵌入式 Qdrant。代价是本地只能运行一个 API 进程、不能水平扩展 worker。

五、嵌入模型与自定义

本项目实际使用哪个嵌入模型？

通过 run.bat 启动时，当前实际配置为：

  • Provider：fastembed
  • 模型：BAAI/bge-small-zh-v1.5
  • 向量维度：模型自动检测为 512
  • Sparse 检索：字符级 BM25，不需要神经网络模型

代码的零配置兜底是 hash 384 维，它用于离线测试，不是真正的语义嵌入模型。

默认嵌入模型能否自定义？

可以。主要环境变量如下：

环境变量用途
KB_DENSE_PROVIDERfastembed、openai 或 hash
KB_DENSE_MODEL模型名称
KB_DENSE_DIM向量维度；FastEmbed 会优先探测实际维度
KB_DENSE_BATCH_SIZE嵌入批大小
KB_MODEL_CACHE_DIR本地模型缓存目录
KB_OPENAI_BASE_URLOpenAI 兼容嵌入服务地址
KB_OPENAI_API_KEYOpenAI 兼容服务密钥

本地 run.bat 会提供 FastEmbed 默认值，但尊重外部已经设置的环境变量；自定义 provider 和模型无需再修改脚本硬编码。

更换嵌入模型后，已有文档需要重新上传吗？

不需要重新上传或重新解析，但必须重新生成全部向量：

run.bat reembed

reembed 会复用已经保存的 chunk，重建 Qdrant 集合。若不重建，新旧向量语义空间不一致；维度不同时还会直接报错。
