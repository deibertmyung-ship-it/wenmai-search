二、文档格式与解析器

项目目前支持解析哪些文档格式？

解析器主要格式说明
内置 TextParser txt、md、markdown、text、rst、log、csv 直接解析，不需要模型或外部服务
Docling pdf、docx、pptx、xlsx、html、图片等 默认富文档解析器
Unstructured doc、ppt、xls、epub、eml、msg、rtf、odt，以及常见 PDF/Office/图片 Docling 失败时的通用降级解析器
Marker pdf 面向 PDF 的高质量兜底解析器

默认解析链为：docling → unstructured → marker；纯文本输入始终优先使用内置解析器。

部署时是否会自动安装 Docling、Unstructured、Marker？

已将三者从可选依赖调整为后端核心依赖。标准 Python 安装和 Docker 镜像构建都会安装三种解析器；Docker 还会安装 libmagic、Poppler、Tesseract 等常见 PDF/OCR 系统组件，并在构建阶段校验项目实际使用的 import 路径。

Marker 当前固定在兼容现有适配器的 1.x 版本，避免 2.x 公共 API 变化导致运行时错误。

安装三个解析库后，还需要配置相关 API 吗？

不需要。当前实现中三者都在本机进程内解析：

  • Docling 使用本地 DocumentConverter。
  • Unstructured 使用本地 partition。
  • Marker 使用本地模型推理。

部分 PDF/OCR 首次解析可能下载模型权重，因此需要允许首次联网或预先准备模型缓存，但这不是解析 API，也不需要 API Key。

三、Word 上传与后台任务

为什么上传 Word 后任务一直未完成？

诊断时发现两个独立问题：

  1. 任务状态为 pending、尝试次数为 0，说明没有 worker 领取任务。
  2. 当时环境没有安装 Docling、Unstructured 或 Marker；即使 worker 启动，DOCX 解析也会因缺少依赖失败。

处理后，文档“承载网规划管理岗位知识点汇编.docx”状态已变为 completed，成功生成 75 个 chunk，当前版本已写入索引。

为什么上传后不自动解析，还要手动运行 run.bat worker？

问题发生时，本地工作流把“登记任务”和“执行任务”分开：

Web 上传 → 文件落盘 → 创建 pending 任务 → worker 解析/切分/嵌入/索引

旧版 run.bat 只启动 API 和 Web，不启动常驻 worker。安装解析库只能保证 worker 能解析文件，不能自动启动 worker。

另外，旧版本地使用嵌入式 Qdrant，同一数据目录不能由独立 API 与 worker 进程同时占用。因此 run.bat worker 会暂时停止 API、排空队列，然后恢复 API。

该限制现已解决：本地仍使用嵌入式 Qdrant，但 worker 改为 API 进程内的常驻线程，与请求线程共享同一个 Qdrant 客户端。

正式部署后也需要手工运行 worker 吗？

不需要。完整 server profile 使用独立常驻 worker；Windows local profile 由 API 生命周期 自动启动内置 worker。run.bat worker 仅作为兼容命令重启整个本地栈。

四、Qdrant 基础

Qdrant 是什么？

Qdrant 是一个向量数据库，用于保存文档向量并查找语义最相近的内容。它不负责解析 Word，也不负责生成最终回答。

文档 → 解析文字 → 切分 chunk → 嵌入模型生成向量 → Qdrant 保存并检索

例如用户搜索“光缆一公里有多少延迟”，即使原文写的是“光纤传输 1km 的时延约为 5μs”，向量检索仍有机会根据语义相似度找到它。

“本地使用嵌入式 Qdrant”是什么模式？

“嵌入式”表示 Qdrant 不作为独立服务运行，而是由 Python 直接打开本地目录：

QdrantClient(path=".kbdata/qdrant")
模式优点限制
嵌入式 Qdrant无需 Docker、端口和独立服务本地目录有进程独占限制
Qdrant ServerAPI 与多个 worker 可同时连接需要运行服务或容器

这里的“嵌入式”是部署方式，不是“文本嵌入模型”。当前项目本地默认使用该模式，数据位于 .kbdata/qdrant；server profile 才使用独立 Qdrant Server。

什么是 Sparse 检索？

Sparse（稀疏）检索主要依据关键词、字符或词项是否匹配。本项目使用字符 1-gram / 2-gram 与 BM25，特别适合中文专有名词、设备编号、标准号和原文措辞。

检索方式判断依据擅长场景
Sparse / BM25关键词和字符匹配G.655、PTN7900、5μs/km 等精确内容
Dense / 向量语义相似度查询与原文说法不同但意思相近

项目将两路结果通过 RRF 融合：Dense 负责“意思像不像”，Sparse 负责“关键词对不对”。

本地切换到独立 Qdrant Server 和常驻 worker，工程量和依赖大吗？为什么最初没有默认这样设计？

核心后端原本就支持 KB_QDRANT_URL 和常驻 kbsvc worker，所以改造量主要在本地编排、进程管理、健康检查、日志和旧索引迁移，属于小到中等工程。

无需新增 Python 依赖；需要 Docker Desktop（或 Docker Engine）运行 Qdrant Server。最初选择嵌入式模式，是为了做到不安装 Docker 即可演示，但牺牲了 API 与 worker 并行运行能力。

曾完成独立 Qdrant Server 方案，但评估 Docker 依赖后，最终本地方案调整为：

SQLite + 本地文件存储 + 嵌入式 Qdrant + API 内置 worker
  • run.bat 只启动 API 与 Web，不需要 Docker。
  • 上传任务自动处理，不再要求手动排空队列。
  • API 请求与 worker 线程共享进程级 Qdrant 单例，并串行化嵌入式读写。
  • 需要多 API 或多 worker 时，再切换完整 server profile。

为什么独立 Qdrant 方案需要 Docker？没有 Docker 能否实现？

Qdrant 本身不强制依赖 Docker；Docker 只是负责稳定运行独立服务、固定版本、映射端口和保存数据卷。也可以使用原生 Qdrant、WSL、Podman 或远程 Qdrant。

对于本项目的单机使用场景，最终选择更轻量的无 Docker 方案：将 worker 放进 API 进程，使它和请求线程共享嵌入式 Qdrant。代价是本地只能运行一个 API 进程、不能水平扩展 worker。

五、嵌入模型与自定义

本项目实际使用哪个嵌入模型？

通过 run.bat 启动时，当前实际配置为：

  • Provider：fastembed
  • 模型：BAAI/bge-small-zh-v1.5
  • 向量维度：模型自动检测为 512
  • Sparse 检索：字符级 BM25，不需要神经网络模型

代码的零配置兜底是 hash 384 维，它用于离线测试，不是真正的语义嵌入模型。

默认嵌入模型能否自定义？

可以。主要环境变量如下：

环境变量用途
KB_DENSE_PROVIDERfastembed、openai 或 hash
KB_DENSE_MODEL模型名称
KB_DENSE_DIM向量维度；FastEmbed 会优先探测实际维度
KB_DENSE_BATCH_SIZE嵌入批大小
KB_MODEL_CACHE_DIR本地模型缓存目录

本地 run.bat 会提供 FastEmbed 默认值，但尊重外部已经设置的环境变量；自定义 provider 和模型无需再修改脚本硬编码。

更换嵌入模型后，已有文档需要重新上传吗？

不需要重新上传或重新解析，但必须重新生成全部向量：

run.bat reembed

reembed 会复用已经保存的 chunk，重建 Qdrant 集合。若不重建，新旧向量语义空间不一致；维度不同时还会直接报错。

八、三种检索模式是否真的对应三条后端路径

混合 / 语义 / 字面，切换时后端真的走不同逻辑吗？

是，三条路径都是真的。但项目原有的测试证明不了这一点—— test_every_retrieval_mode_returns_results 只断言「三种模式都有结果」， 即使 mode 被完全丢弃，这个断言照样通过。所以我写了能证伪的探针，对运行中的系统实测：

检查hybriddensesparse
实际跑了哪些召回器[dense, sparse][dense][sparse]
融合权重1.0 / 1.01.0 / 0.00.0 / 1.0
计时字段两个都在只有 dense_search只有 sparse_search
候选数20 / 2020 / 00 / 20

最硬的证据：hybrid 融合前，dense 与 sparse 的 top-8 重合度 0/8—— 两路返回完全不同的候选，不可能是同一条代码路径。另外 mode=magic 返回 422，不是静默回退。

既然模式是真的，为什么界面上「混合」和「字面」经常看起来一样？

因为 lexical reranker 把混合模式拉回了字面模式。召回层确实是混合的，但默认的 KB_RERANKER=lexical 按字面重合度重排，系统性地把 sparse 候选顶上来：

查询rerank ON ∩sparsererank ON ∩densererank OFF ∩sparse

涉害深者为用1.00（完全一致）0.110.33
昴星课如何取用0.670.330.11

关掉 rerank 后 hybrid 与 sparse 只重合 0.11–0.33，说明融合是真的。不是模式没接通，是重排器把 dense 的贡献洗掉了。

十、5.6 秒瓶颈的根因

为什么每次检索要 6 秒以上？

实测拆解：

              sparse_search    dense_search
贼克如何取用神      5632 ms         391 ms
涉害深者为用        5638 ms         399 ms
昴星课如何取用      5392 ms         383 ms

字面检索比语义慢 14 倍，占 hybrid 总耗时的 93%。按查询长度扫描后发现 约 4.9 秒是固定成本，只有 ~20ms/词是可变的。

根因不在 BM25、不在字符 n-gram、也不在 Qdrant 引擎，而在 嵌入式 qdrant-client 的 local 模式根本没有稀疏倒排索引：

# qdrant_client/local/sparse_distances.py:109-121
for vector in vectors:                        # 22,659 次纯 Python 循环
    score = sparse_dot_product(query, vector) # 内部还有 2 次 assert is_sorted 全扫

同一模式下 dense 只要 390ms，因为它走 numpy（C 实现）。qdrant_store.py:81 的注释其实早就承认了： 「Embedded Qdrant scans payloads directly」。

在换引擎之前，有哪些免费的优化？

我提出了两个，其中一个经实测是无效的，没有做。

① 多变体合并为单次扫描 —— 做了。改写的每个变体原本各跑一遍全库扫描：

查询变体数改前改后结果重合
贼克如何取用神15,587ms5,599ms1.00
什么是涉害210,571ms5,317ms1.00
解释一下昴星课以及遥克课316,356ms5,654ms1.00

延迟从「随变体数线性增长」变成常数，而且结果重合度全部 1.00——连融合前的原始召回排序都逐位一致。 原因可以证明：rewrite 只做减法，所以每个变体都是原查询的连续子串， 字符 n-gram 必然是原查询的子集，取并集就等于原查询自己。也就是说改写变体对稀疏检索本来毫无贡献，纯粹白烧 5 秒一次。

② 调低 overfetch —— 我判断错了，没有做。我原本说「local 下调到 2 能省掉一半」。实测：

top_k   limit   sparse_search_ms   rerank_ms
    1       4           5633.9         1.7
   10      40           5608.3        13.3
   25     100           5598.9        33.7

limit 变化 25 倍，扫描时间纹丝不动——因为 calculate_distance_sparse 对全部向量算完分才截断， limit 根本不进入扫描成本。调低它只会白白损失召回深度，换来 30ms。 做一个已知无效还有副作用的改动，比不做更糟。

「支持模糊搜索」能作为立项理由吗？

不能。Tantivy 的 fuzzy_term_query 是编辑距离匹配。原型实测：

fuzzy('涉宝', distance=1) -> 返回「三井 / 壬子癸 / 天河」等完全无关内容

汉字的编辑距离没有语义含义——「涉害」和「涉宝」距离是 1 但毫无关系。而且 现有的字符 n-gram BM25 本身已经是一种模糊匹配，错一个字仍能命中大部分词项。

结论：上 Tantivy 是为了速度和删掉自研 BM25，不是为了模糊搜索。

十二、繁简/异体字与拼音搜索

项目支持繁简归一化和拼音搜索吗？

原本两个都不支持，而且繁简这条不是理论问题——语料本身就是混排的：

简 阴 × 44,548    繁 陰 ×   524
简 发 × 15,707    繁 發 ×   512
简 阳 × 41,610    繁 陽 ×   402

不归一化时，词法一路查 阴阳 与查 陰陽 重合 0/10，完全不相交。 dense 靠模型部分容忍，但只有 2–5/10，不能算「支持」。

拼音方面：sparse 返回 0 条（正确）；dense 对 zeike 返回 5 条，但那不是命中—— ANN 检索对任何输入都会返回 top-k 最近邻。别把它当作「支持拼音」。

为什么不用「同时索引简繁两种形式」？

试过，被数据否决：双写结果 100% 偏向繁体。

对         简  繁  双写   双写∩简   双写∩繁
阴阳/陰陽   10  10   10    0/10     10/10
发用/發用   10  10   10    0/10     10/10

原因是 BM25 的 IDF：陰 只出现 524 次、阴 出现 44,548 次， 稀有形式 IDF 高得多，直接主导打分，把常见形式挤出结果。 正确做法是折叠到单一形式——它把两边的 doc frequency 合并，而不是让它们竞争。

实现时最关键的三个约束是什么？

  1. 只作用于检索表示，绝不改写存储文本。 payload.text 是渲染 snippet 与引文的依据，改写古籍原文等于篡改。实测验证： 
    用【简体】「阴阳」检索 → 召回纯繁体的《天無陰陽篇》
snippet: 天無陰陽篇第一 經曰：天圓地方，本乎陰陽。陰陽旣形，逆之則敗…
高亮[2:4] = '陰陽'    ← 偏移精确落在繁体形上
  2. 必须长度守恒。citation.build_snippet 用 str.find 定位高亮并返回偏移量， 归一化若改变长度会让偏移静默漂移。因此自建严格 1:1 字符映射表 （4,300 条，从 zhconv 逐字提取并校验零条非 1:1），而不是整串调 convert()。 用 zh-hans 而非 zh-cn——后者会做大陆词汇替换（軟體 → 软件），改写古籍用词不是我们该做的事。
  3. 领域保护名单。zhconv 把 乾 折叠成 干（取「干燥」义）， 但查过语料上下文后发现本语料中 乾 全是卦名： 
    乾为 × 2,806    乾坤 × 2,749    乾之 × 1,089    乾卦 × 293
…仲月辰巽及乾坤。季月乙丁与辛癸…
…没四维乾坤艮巽，大吉，百事无碍…
    与巽/艮/坤同现，零个干燥义。折叠会把「乾坤」和「干支」（25,748 次）合并——两个核心且无关的概念。 已验证两者检索重合 0/10。这是查过语料才定的，不是想当然。

最终效果？

两路都做且都在单一入口：词法侧在 tokenize() 内部折叠（索引与查询共用同一函数）； 稠密侧用 FoldingDenseEmbedder 包装嵌入器——那里有 worker / reembed / pipeline 三个调用点，包装比在每处写一遍更难漏。成本可忽略：str.translate 走 C 实现，120 万字 65ms。

拼音搜索为什么建议不做？

技术上可行（pypinyin + Tantivy 加一个 body_pinyin 字段），但三个理由不划算：

  1. 同音字爆炸。liuren 会同时匹配「六壬」「流人」「留任」「柳仁」。
  2. 文言文多音字消歧不准。壬、行、重、度—— pypinyin 的消歧模型按现代汉语训练，对文言文经常判错，而错的读音会静默污染索引。
  3. 与产品定位冲突。这套系统的价值主张是「给出可核对的出处」， 拼音检索天然模糊，降低的正是它最想保证的东西。

真正的中文「模糊」需求是繁简、异体字、OCR 错字——前两类用归一化表解决更对路，也便宜得多。

十四、嵌入式 Qdrant 没有 HNSW，影响是什么

先纠正：之前对这一条的解释是错的

性能文档里原本写着「396ms 是全量扫描，之所以还能接受是因为 numpy 是 C 实现」。 把耗时拆开测之后发现这个解释站不住：

环节耗时
查询嵌入（ONNX bge-small-zh）2.3 ms
22,659×512 全量点积 + argsort（纯 numpy）1.23 ms
实测 dense_search385 ms

numpy 部分只占 0.3%，还有 380ms 不知去向。真正的开销是 qdrant-client local 模式在 Python 层逐点做的对象处理， 和 numpy 快不快没关系。文档已订正。

实际的扩展行为是怎样的？

用独立的 local Qdrant 实测（纯净集合，排除嵌入与业务代码干扰）：

N无过滤带过滤每点耗时
1,0003.0 ms11.2 ms3.03 µs
5,00017.2 ms56.1 ms3.44 µs
10,00036.5 ms112.1 ms3.65 µs

严格线性，每点约 3.5 微秒。而纯 numpy 点积每点只要 0.05 微秒—— 70 倍的差距全在 Python 开销上。有 HNSW 时是 O(log N)， 下表每一档都在 1–5ms，基本不随规模变化。

语料规模无过滤带过滤
22,659 段（当前）~385 ms（实测）~501 ms（实测）
100,000 段~1.4 s~4 s
500,000 段~7 s~20 s

触发点约在 10 万段，是现有语料的 4 倍。另有隐性成本：local 模式把 全部向量常驻内存，22,659×512×4B ≈ 46MB 现在无所谓，100 万段就是 2GB。

最反直觉的一条：加过滤条件会让检索变慢

看 local_collection.py 的执行顺序——先对全部向量算分，再算过滤掩码：

590:  scores = calculate_distance(query_vector, vectors, distance)   # 全部向量
653:  mask  = self._payload_and_non_deleted_mask(query_filter, ...)  # 之后才过滤
668:  order = np.argsort(scores)[::-1]                               # 全量排序，非 top-k

过滤不减少计算量，反而要额外遍历全部 payload 做掩码。实测：

无过滤（22,659 段）                385.5 ms
按 source 过滤                     501.0 ms   +30%
按单个 document 过滤（约 30 段）     505.4 ms   +31%

把范围收窄到 0.13% 的语料，反而慢 31%。

这条最有实际影响：界面上勾选「来源」「限定章节」，直觉是缩小范围会更快， 实际是更慢。服务端 Qdrant 有 payload 索引与过滤下推，行为正好相反。

顺带一提，np.argsort 是 O(N log N) 全量排序，只取前 40 条用 argpartition 就够，实测 1.23ms → 0.70ms。属上游库实现，未改。

除了慢，嵌入式还失去了什么？

能力影响
HNSW 索引O(log N) → O(N)
payload 索引 + 过滤下推过滤从「缩小搜索空间」变成「纯加成本」
标量 / 乘积量化内存占用本可降到 1/4–1/32
多进程并发嵌入式持目录锁，只能一个进程
快照备份只能停服务复制目录

词法一路已经不受这个问题影响——Tantivy 是真正的倒排索引， 2.5ms 且过滤是下推的，所以 mode=sparse 端到端只要 16ms。

现在该怎么办？

  1. 短期不用动。385ms 在可接受范围，且瓶颈已从 5.6 秒降到 413ms。
  2. 但有一件事值得立刻做：界面上的过滤条件会让检索变慢而非变快， 与用户直觉相反，应在 UI 上提示或在文档中写明。
  3. 语料接近 10 万段时，切 Qdrant Server 是唯一有效手段—— 这不是调参能解决的，嵌入式模式根本没有索引可调。但那会引入 Docker， 与 run.bat 的「无 Docker」设计目标冲突，届时需要重新权衡。

十六、拓扑选择

要提高检索性能，是否必须上完整的 server profile？

不是。这里有两条收益不同、成本差很多的路：

方案检索延迟收益额外收益成本
仅 Qdrant Server + 本机进程 全部 无 一个容器，不改代码

关键判断：Postgres 与 MinIO 对检索延迟没有任何贡献。 延迟收益全部来自 Qdrant Server 的 HNSW 与 payload 索引下推。选完整方案是为了 生产化，不是为了更快。

十七、词法索引在 compose 里静默失效

部署前审查 compose，发现了什么？

原模板里 api、worker×2、mcp 三类容器 都没有挂载 KB_DATA_DIR 卷。而 Tantivy 是进程内库， 索引就是文件系统上的一个目录。后果：

  1. worker 容器把词法索引写进它自己那一层的 /app/.kbdata/lexical；
  2. api 容器读它自己那一层的同名目录——是空的；
  3. 于是 mode=sparse 恒返回 0 条，hybrid 静默退化成纯 dense。
不会报任何错。索引目录不存在时 Tantivy 会新建一个空索引， 查询正常返回、只是没有结果。唯一的信号是 /v1/stats 里 lexical_docs 与 chunks 对不上。

讽刺的是 05-performance.md 里早就写了「server profile 下需要让词法 写入集中在单一写入者后面」——结论写对了，compose 没有实现它。

怎么修的？

三件事：

  1. 共享卷。三类容器挂同一个 kbdata 卷到 /data，词法索引与 ONNX 权重各一份。
  2. 读侧 reload。Tantivy 的 reader 只在 reload() 时 才看到新段。写进程在 _commit 里已经 reload，但只读进程永远 停在启动那一刻的段集合上。新增 _refresh_reader()， 按 1 秒节流；写进程走 _writer is not None 直接跳过。
  3. worker 副本降到 1。见后文「两条硬约束」。

配了回归测试：同一目录上建两个 store，reader 先 ensure_ready() 再由 writer 写入，断言 reader 能查到。去掉修复后该测试失败 （assert [] == ['chunk-1']），不是摆设。

端到端验证：从 api 容器发 mode=sparse 请求，命中 12 条—— 这正是原模板下会返回空的地方。

十八、三次构建失败与一次误判

第一次失败：apt 装不上

apt-get 连不上 deb.debian.org，exit 100。 容器内实测 80 和 443 端口都通，重跑同一条命令即成功——瞬时网络故障， 没有为此改 Dockerfile 加镜像源。

第二次失败：buildkit 掉线，以及我判断错的地方

报错 rpc error: code = Unavailable desc = error reading from server: EOF， 日志里满屏「临时目录删不掉」，且三个后台任务被同时杀掉。

我的第一判断是磁盘空间不足：宿主 C: 盘只剩 13.3 GB， 而这个镜像要装 torch 全家桶。据此还向用户提出了「把 Docker 磁盘映像迁到 F: 盘」 的方案。

这个判断是错的。查 settings-store.json 发现 CustomWslDistroDir 早已指向 F:\docker\wsl\DockerDesktopWSL，数据盘 docker_data.vhdx 就在 F: 上，那里还有 202.5 GB 空闲。 C: 盘的余量与这次构建毫无关系，不需要迁移任何东西。

容器内 df 显示 950 GB 可用是稀疏 VHDX 的假象，我当时用它反推 「宿主受限」，方向对了但落点错了。真正的原因是内存： 宿主 16 GB 只剩 2.6 GB 空闲，4 核；WSL2 VM 在 pip 解析安装 torch 时被压垮， Docker 引擎重启——这同时解释了 EOF 和后台任务被集体杀掉。

怎么让它构建成功的？

改 Dockerfile 两处：

  1. torch 改用 CPU-only 索引 （--index-url https://download.pytorch.org/whl/cpu）。 默认 Linux wheel 会拖进约 5 GB 的 nvidia CUDA 库，而 compose 拓扑里根本没有 GPU ——纯粹的死重，也是内存峰值、构建时长和镜像体积的最大来源。
  2. pip 拆成三层（torch → 其余依赖 → 校验 import）。 构建再被打断时能从缓存续，而不是从头重下 torch。

结果：镜像 4.26 GB，构建通过。

第三处：源码改一行，依赖重装 20 分钟

原 Dockerfile 把 COPY src ./src 放在 apt 与 pip 之前， 于是任何源码改动都会让下面所有层失效，包括那个 20 分钟的 torch 安装。部署过程中改了三次代码，每次都要重来。

改为标准做法：先只 COPY pyproject.toml，用一个 stub 包 (touch src/kbsvc/__init__.py) 让 pip 能构建元数据，装完依赖后再 COPY src 并 pip install --no-deps --force-reinstall .。

这一处截至文档写作时尚未验证通过。触发的重建两次都挂在 apt 层 （与第一次同样的网络瞬时故障，与层序改动无关），仍在重试中。 在跑通之前不应认为它没问题。

十九、引导过程中暴露的四处缺陷

kbsvc init 报 PermissionError

PermissionError: [Errno 13] Permission denied: '/data/lexical'。 命名卷是 root 所有，容器以 uid 10001 运行。

Docker 会用镜像中被覆盖路径的属主来初始化新卷，而镜像里根本没有 /data。修复：RUN mkdir -p /data && chown kbsvc:kbsvc /data， 放在 useradd 之后、USER 之前，再删掉已建的 root 属主卷。

顺带给 kbsvc init 加了一步：显式建出空的 Tantivy 索引。 否则 api / worker / mcp 同时启动时会并发对空目录调 tantivy.Index(schema, path=...)，是个竞态。

MCP 容器起来了，但连不上

日志：Uvicorn running on http://127.0.0.1:8000——既不是 0.0.0.0 也不是 8078，端口映射自然全落空。

原因：compose 里用 FASTMCP_HOST / FASTMCP_PORT 传参， 那是 mcp<2 时代 FastMCP 的 pydantic-settings 约定。 实际装的是 mcp 2.0.0，mcp.server.fastmcp 模块已不存在， 走的是 MCPServer 分支，它完全不读这两个环境变量， bind 地址是 run() 的关键字参数。

这类失效最难发现：环境变量拼写没错、容器也正常启动、健康检查还是绿的 （因为镜像的 HEALTHCHECK 探的是另一个端口）。

修复：给 kbsvc mcp 加 --host / --port 显式传参，compose 改用命令行参数。验证：initialize 握手 200， tools/list 返回三个只读工具。

worker 和 mcp 永远 unhealthy

镜像的 HEALTHCHECK 探 127.0.0.1:8077/healthz。worker 不提供 HTTP， mcp 在 8078，两者都必然失败。修复：worker 用 healthcheck: disable: true，mcp 覆盖为探 8078。

这一条不影响功能，但它掩盖了上一条真实的故障——mcp 本来就该是 红的，只是分不清是配置问题还是探针问题。

导入命令返回 registered=0，且不报错

kbsvc ingest /corpus 登记了 0 个文件，但容器里 ls /corpus 明明有 205 个。

是 Windows git bash 的 MSYS 路径改写：/corpus 作为命令行参数被转成了 Windows 路径。代码里 path.resolve() 对不存在的目录不报错， rglob 返回空，于是安静地登记了 0 个文件。

加 MSYS_NO_PATHCONV=1 前缀后正常：registered=202， 与文档基线一致。

另外 CLI 导入必须加 --no-run-worker—— 它默认会在自己进程里 drain 队列，而 worker 容器已经持有 Tantivy 的写锁。

二十一、两条硬约束

worker 真的可以水平扩展吗？

不能。上限是 1 个进程。

任务表的租约机制确实支持水平扩展，但 Tantivy 挡在前面：它是进程内库、持目录 独占锁，而 worker 在 ingest/worker.py 里内联写词法索引。 第二个副本抢不到 writer 会失败。

README 的「独立常驻 worker，可水平扩展」与 05-performance.md 的 「切 server profile 后多开 worker：--scale worker=4」 描述的是任务队列的能力，不是当前部署的能力。两处均已订正。

要真正扩 worker，得先把词法写入收敛到单一写入者背后（独立的 lexical-writer 服务，或一个专门的任务类型）。

那导入慢该怎么解决？

既然瓶颈是嵌入算力而不是并发度，加 worker 副本方向就是错的 （何况也加不了）。有效方向是更快的 CPU、GPU，或把 KB_DENSE_PROVIDER 指向外部推理服务（vLLM / TEI）。

一句话概括这次部署的收益边界：server profile 解决的是「检索」的扩展性 （HNSW、过滤下推、多进程并发、无 store_init），「导入」吞吐仍然取决于嵌入算力。

二十三、worker 水平扩展方案设计

worker 为什么只能跑一个副本？

两个原因叠加：Tantivy 是目录级独占写锁，同一索引目录只允许一个写入者； 而词法索引的写入内联在 ingest 任务里——每个 worker 处理文档时都要自己写一次倒排。 两者相加，worker 副本数的硬上限就是 1。

这次的目标经确认是先拆掉架构天花板，不是追吞吐。 吞吐受限于嵌入计算（08-06 实测 4.4 段/秒），多开 worker 在当前机器上也快不了； 但「结构上不允许多副本」和「多副本收益有限」是两件事，前者值得先解决。

选了什么方案？

专职 lexical-writer + 词法任务队列：ingest worker 不再直接写 Tantivy， 改为入队词法任务；单独一个 lexical writer 进程消费队列并独占索引目录。 ingest worker 由此可以任意水平扩展。

ingest worker（N 个）→ 入队 lexical_* 任务 → ingest_job 表 → lexical writer（1 个）→ Tantivy

问题处理

设计过程中发现了什么原本不在目标内的问题？

二十八、lexical 精排的实现

有没有用 langchain？

没有，整个项目零 langchain。三个层面都验证过：源码 grep （含 llama_index / haystack）无匹配、pyproject.toml 无声明、 运行中容器 pip list 连传递依赖都没有。检索链路全是直接用底层库自己拼的。

打分公式是什么？

score = 0.7 × coverage + 0.2 × min(density, 1.0) + 0.1 × earliness
分量计算
coverage命中的不同查询词 / 查询词总数
density命中总次数 / (√分块长度 + 1)
earliness1 − 首次命中下标 / 分块长度

关键在 tokenizer，不在公式。tokenize() 对 CJK 同时产出一元和二元组， 贼克如何取用神 展开成 13 个 token（7 个一元 + 6 个二元）。 这带来一个不明显的性质：二元组隐式承担了词序/短语约束—— 原文出现完整短语则 coverage 接近 1，只是零散地各处出现这几个字则上限约 7/13 ≈ 0.54。

分词前过 normalize()（繁简/异体折叠）和 lowercase，与索引侧共用同一函数，两边不会不一致。

在流水线里排序键是 (−精排分, −融合分)，RRF 分数退化为 tiebreaker； 输入是全部候选而非前 10，所以它能把第 40 名提到第 1 名。

两处更正。其一，文件 docstring 写 density 是 “log-damped”， 但代码是 len(tokens) ** 0.5——平方根抑制，不是对数，注释错了。 其二，我此前说改进 lexical 精排「仍是亚毫秒级」，那是引用文件头的 “sub-millisecond” 注释而未验证。 实测 40 个候选 17.56ms，占当时 88ms 总耗时的约 20%。 这修正了「改进它是零成本」这个前提，也直接引出了下一节的工作。

三十二、字体是设备彩票

问题是什么？

tokens.css 的字体栈是纯本机依赖：

--font-serif: "Songti SC", "SimSun", "Noto Serif CJK SC",
              "Source Han Serif SC", "STSong", Georgia, serif;

macOS 命中 Songti SC；Windows 落 SimSun（点阵感重，与「善本」意象相悖）； Linux 大概率一路 fallback 到 Georgia，再由浏览器兜底任意 CJK 字体。

整个「古籍善本」方向建立在字体上，而字体此前不受控。 这条是读代码直接证实的，不依赖外部佐证。

怎么解的？

deploy/build-fonts.py 在部署期抓取两套 OFL-1.1 字体， 经 cn-font-split 切成 unicode-range 分片：

用途字体分片数总大小
正文Noto Serif SC38217.0MB
标题与注文霞鹜文楷 LXGW WenKai31312.2MB

浏览器只下载页面实际用到的那几片——整套 CJK 衬线 25MB，一页文言文只要几十 KB。 每个 @font-face 的 src 里 local() 排在前面， 本机已装则完全不下载。

字体栈相应拆成 --font-song / --font-kai， --font-serif 保留为前者的别名，现有规则一行未改。 刻本用宋体排正文、楷体排题注，据此把 .reader__title 与 .chunk__heading 改用楷体——「字体对比而非字号对比」此前只兑现了一半。

不跑这个脚本会怎样？

页面回落本机字体栈，即加这套之前的行为。base.html 只在分片确实存在时 才 link 字体样式表，所以不会出现一堆 404。

判断依据是分片清单而非 fonts.css——后者是生成物， 可能在有人删掉分片目录后留在工作区，那时若照它判断就会 link 一个每个 @import 都 404 的样式表。这个「陈旧样式表」分支有专门的测试守着。

产物（分片 + fonts.css）已 gitignore，不进版本库。 整件事是部署期一次性成本，不是运行时依赖； npx 只在这个脚本里用一次，应用本身不引入任何 npm 依赖。

cn-font-split 报了个崩溃，为什么还继续？

它在 Windows 上以 3221225477（0xC0000005，访问违例）退出， 但全部分片与清单都已写出——崩在 wasm 运行时收尾阶段，工作已经做完。

处理方式不是忽略退出码，而是改为以产物为准：校验清单存在、 每个 URL 引用可解析、每个目标文件确实以 wOF2 开头（而非截断的下载）。 真失败仍然失败——清单缺失或引用悬空就抛错并打印 cn-font-split 的输出尾部。

过程中还踩了一次自己造成的坑：先前为核查产物 cd 进了分片目录， 而 shell 的工作目录跨调用保持，于是清理时 rmtree 撞上 WinError 32。脚本因此加了带退避的重试，且重试耗尽仍会明确报错而不是静默跳过。

三十三、无脚本承诺与它抓到的 bug

原来是怎么保证的？

kbweb 一直承诺「JS 全部失效时页面仍可检索、翻页、上传」，但此前只有 e2e 里一个降级测试守着（关掉 JS 后阅读器仍可翻页），其余全靠人工验收。

照 whoogle-search 的做法改成配置维度：新增 KBWEB_NOJS，为 true 时 服务端一个 <script> 都不发；tests/conftest.py 的 config fixture 参数化，整个视图测试套件在 js / nojs 两个维度下各跑一遍。测试数 37 → 87，覆盖率 85%。

whoogle 用的是随机化，这里改成参数化——确定性比随机覆盖更适合当回归门禁。

模板侧只需一处：base.html 用一个 {% if not nojs %} 同时门控自身脚本与子模板的 scripts 块，所以新增页面无法绕过这道门。

抓到了什么？

一个真 bug，而且 README 里对它的描述是错的。

partials/_debug.html 的抽屉带 hidden 属性， 且只有 drawer.js 能揭开它。README 写的是「抽屉内容仍在 DOM 中，可滚动查看」—— 不成立：hidden 让它完全不可见。无脚本时检索轨迹在 DOM 里， 却永远不显示。

这比不发轨迹更糟：页面声称给了调试负载，实际从不展示。

改法是把面板体抽到 _debug_body.html，两种形态共用同一份内容—— 有脚本时是覆盖抽屉，无脚本时以 .drawer--inline 内联渲染在结果之后。 同时移除两个无脚本下点了没反应的死控件：主题切换按钮（主题仍跟随 prefers-color-scheme）与调试抽屉开关。

这些测试真的有牙齿吗？

做了变异测试验证：把 _debug.html 改回「永远渲染覆盖抽屉」， test_retrieval_trace_is_readable_without_scripts[nojs] 立刻失败； 还原后 18 个全过。

断言写成在两个维度下都成立的形式，而不是在某个维度下 skip， 例如 assert ("<script" in body) is not config.nojs—— 这样两个方向的回归都会失败。

一处需要小心的地方：assert "hidden" not in body 会误伤， 因为检索表单本来就有一个合法的 <input type="hidden"> 标记位（即 08-05 那个 f=1）。改为断言覆盖层标记 data-drawer / data-scrim 不存在。

三十四、CJK 排版与一次自我推翻

加了什么？

三条，只作用于语料实际渲染的两处（检索片段与阅读器切块）， 界面 chrome 是短句无衬线标签，无收益：

  • line-break: strict——收紧 auto 仍允许而禁则不允许的 剩余情形（小假名、〜、‐ 等）
  • text-spacing-trim——收掉连续全角标点（」「、。）内部叠加的字身空隙
  • text-autospace——中西文之间补四分之一空

后两者均以 @supports 包裹，不支持时按现状排版，零运行时成本。 heti 用改写 DOM 成 <h-char> 的方式做同样两件事， 会与命中高亮产生的 <mark> 打架，故不引入。

另从 heti 取了一个实测约束写进 tokens.css 注释：着重号最小可用行高 1.7、 ruby 最小 2.0。--leading-read: 1.95 正好卡在能上着重号、ruby 会挤的位置—— 以后有人想调低会看到理由。

哪条判断被自己推翻了？

调研文档初稿里我断言「kbweb 现在的 CSS 没有任何标点避头尾处理， 长文里『。』『，』跑到行首会立刻露怯」。这句话是错的。

浏览器默认就按 UAX #14 断行，句读本来就不会出现在行首；而 .result__snippet 与 .chunk__text 早已带了 hanging-punctuation: allow-end，那正是行尾悬挂标点。

真实增量比初稿声称的小得多——只剩 line-break: strict， 是收紧，不是修复。调研文档的 md 与 HTML 两版都已加更正说明， 没有把错误判断悄悄删掉。

另有一条来自调研的建议被白盒核查下调：有人提出「偏移量锚点很脆，切块变了就全断」， 建议引入 Hypothesis 的多重 selector 降级链。但 filters.py 的 highlight_segments 已有防御——span 越界或重叠 一律丢弃，坏负载退化为纯文本而非打乱正文；且 text 与 spans 来自同一次响应，天然自洽。真正有漂移风险的只是 /read/ 的深链锚定， 是个小得多的问题。

为什么不做古文段首缩进？

调研结论里列了 heti 的 ancient.scss（古文段落首行缩进 2em）， 但实际没做。

.chunk__text 用 white-space: pre-wrap， 块级 text-indent 只作用于首行——若一个切块内含多个段落 （由 \n 分隔），只有第一段会缩进，其余不会。

那不是移植 heti 规则，是引入排版 bug。已记进文档，等切块粒度确定后再单独处理。

三十六、移植决策与阶段推进

三十七、测试抓到的四个设计缺陷

写测试的过程中改了哪些设计？

四处，都不是「测试没写对」，是设计本身有问题：

缺陷为什么是设计问题
幂等键唯一约束把所有未带键的检测视为键为 '' 而互相冲突 幂等键是可选的。同一调用方发第二个普通请求就会失败。 改为 PostgreSQL 部分唯一索引（WHERE idempotency_key <> ''）

PostgreSQL 测试怎么处理「跑不了」的情况？

抄袭是首个需要真实 PostgreSQL 的测试集（其余全跑 SQLite）。策略是复用 compose 那个实例， 不可用时 skip 并把原因写进报告，明确标注 these assertions did NOT run。

「没跑」和「跑过且没问题」必须能区分，否则绿灯毫无意义。实测无 PG 时 199 项通过 / 79 项 skip，每项都带完整原因。

三十九、环境侧的三次误判

构建失败、服务打不开、429，分别是什么原因？

现象我最初的判断实际
