# ADR-0004：加列迁移写在 init_db 中，不引入迁移框架

- 状态：Accepted
- 日期：2026-08-07
- 决策者：项目维护者
- 影响范围：`knowledge-service/src/kbsvc/db/session.py`
- 触发事件：ADR-0003 需要向已部署的 `chunk` 表增加列

## 背景

项目至今没有 schema 迁移工具。建表依赖 `Base.metadata.create_all(engine)`，由 `init_db()` 在 api、worker、mcp 三个进程启动时各调用一次。

`create_all` 的语义是**只创建缺失的表**。它不会向已存在的表添加模型中新增的列，且不报错。

因此在 ADR-0003 中向 `Chunk` 模型添加 `analyzed` 字段后：

- 全新数据库正常，列由 `create_all` 建出；
- 已部署的数据库（线上 22,345 行）拿不到该列，任何读写都会失败。

项目需要跨 SQLite（local profile）与 PostgreSQL（server profile）两种后端，二者的 `ALTER TABLE` 语法存在差异，且 SQLite 不支持 `ADD COLUMN IF NOT EXISTS`。

## 决策

**在 `init_db()` 中增加 `_apply_additive_columns()`，只处理「向已存在的表增加列」这一种变更。变更集是手写的白名单常量。**

```python
_ADDITIVE_COLUMNS: tuple[tuple[str, str, str], ...] = (
    ("chunk", "analyzed", "TEXT NOT NULL DEFAULT ''"),
)
```

实现使用 SQLAlchemy `inspect()` 读取现有列，缺失才执行 `ALTER TABLE`，因而方言无关且天然幂等。全新数据库上是无操作。

DDL 中带 `NOT NULL DEFAULT ''`：PostgreSQL 11+ 与 SQLite 均可在不重写表的前提下为存量行填入默认值。模型侧对应声明 `server_default`，使两条路径（新建与迁移）产生一致的 schema。

### 明确的边界

**只允许可空或带默认值的加列。** 任何会改写、重命名或删除数据的变更都不属于本机制。

理由是这段代码在**每个进程每次启动时**都会执行。破坏性操作放在这个位置，意味着一次误配或一次回滚部署就可能不可逆地损坏生产数据，且没有审阅、没有版本记录、没有回滚路径。

变更集刻意写成常量而非自动比对模型与数据库的差异：自动比对会把「模型删了一列」解释为「数据库该删列」，正是上面要排除的情况。

## 选择该方案的原因

- 加列是当前唯一的实际需求，且是所有 schema 变更中风险最低的一类；
- 引入 Alembic 需要建立版本目录、基线迁移、离线/在线两套执行路径与部署顺序约定，对当前规模是不成比例的复杂度；
- 三个进程共用 `init_db()`，无需额外的部署步骤或运维文档；
- 白名单常量在 code review 中一目了然，新增一行即可，无需理解迁移框架的状态机。

## 被否决的方案

### 引入 Alembic

否决原因：为一次加列引入完整迁移框架，需要基线迁移、版本表、部署顺序约定与回滚流程。当前 schema 变更频率不足以摊薄这些成本。**但这是本决策的自然继任者**——见「后续决策」。

### 手工在运维手册中记录 SQL，由人执行

否决原因：三个服务共用同一数据库，任一服务先于 DDL 启动就会失败；且本地开发者的 SQLite 库同样需要该列，依赖人工执行必然遗漏。

### 每次启动自动比对模型与数据库并同步差异

否决原因：无法区分「模型新增了列」与「模型删除了列」。后者会被解释为应当删列，把一次代码回滚变成一次数据丢失。

### 让 `create_all` 之外的差异由重建数据库解决

否决原因：线上有 22,345 行已索引数据，重建意味着 2.7 小时的重新嵌入。

## 后果

### 正面后果

- 加列对部署方是透明的，无额外步骤；
- 全新库与存量库最终得到相同的 schema；
- 幂等，可重复执行，可并发（三个进程同时启动时，先到者执行，后到者检测到列已存在）。

### 负面后果

- **本机制不覆盖任何破坏性变更。** 一旦需要改列类型、重命名或删列，必须先引入真正的迁移工具，不能扩展本机制；
- 变更集是手写的，新增列时若忘记同步登记，存量库会静默缺列；
- 没有版本记录，无法回答「这个数据库执行过哪些变更」，只能通过 `inspect()` 观察当前状态;
- 三个进程并发启动时存在竞态窗口（两者同时判定列不存在），依赖 `ALTER TABLE` 本身失败后重启恢复，未做显式加锁。

## 验证要求

已覆盖为单元测试 `test_adding_the_analyzed_column_preserves_existing_rows`：

- 构造一个不含新列的 `chunk` 表并插入数据；
- 执行 `_apply_additive_columns()`；
- 断言列已添加、**既有行数据未被修改**、新列取到 DDL 默认值；
- 重复执行一次，断言幂等。

## 后续决策

以下事项不属于本 ADR，若实施需要应另建 ADR：

- 出现第一个破坏性 schema 变更时，引入 Alembic 并把 `_ADDITIVE_COLUMNS` 转为基线迁移；
- ADR-0001 中 `plag_*` 表的正式 schema migration 工具（该 ADR 已将其列为后续决策，与本条应合并考虑）；
- 为并发启动的 DDL 竞态引入 advisory lock。
