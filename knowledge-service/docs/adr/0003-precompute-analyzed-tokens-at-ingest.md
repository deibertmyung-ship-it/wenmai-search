# ADR-0003：分词结果在 ingest 时预计算并存入 Postgres

- 状态：Accepted
- 日期：2026-08-07
- 决策者：项目维护者
- 影响范围：`db/models.py`、`db/repo.py`、`ingest/worker.py`、`ingest/reembed.py`、`retrieval/rerank.py`、`retrieval/pipeline.py`、`cli.py`
- 实现提交：`a879cca`

## 背景

`LexicalReranker` 对每个候选调用 `tokenize()` 重新分词。实测 40 个候选（均值 626 字符）耗时 **17.56 ms**，约占当时检索总耗时 88 ms 的 20%。

代码注释称该实现为 “sub-millisecond”，与实测不符——这是本次工作的起点。

分词结果只取决于 chunk 文本，是静态的。每次查询重算是纯粹的重复劳动。

## 决策

**在 ingest 时计算 `analyze(chunk.text)` 并存入 `chunk.analyzed` 列；精排读取该列而非重新分词。**

存储位置选 PostgreSQL 新增列，不进向量库或倒排索引的 payload。

### 打分等价性

`LexicalReranker.score()` 新增关键字参数 `tokens`。传入时使用预计算结果，否则退回实时分词。**打分逻辑一字未改。**

验证：5 个查询 × 400 条真实 chunk，预计算与实时分词**逐条同分，0 处不一致**。

这一性质是本方案相对更快替代方案的决定性优势：项目目前**没有检索质量评测集**，任何改变排序的方案都无法验证是好是坏。

### 缺值语义

`analyzed` 为空表示尚未回填，精排逐候选退回实时分词。因此：

- 回填可以随时中断、随时补做；
- 未回填期间只是慢，不会错;
- 加列与回填可以分开发布。

`repo.analyzed_by_ids()` 直接过滤掉空值，使调用方无需区分「没有存储」与「存储了空串」。

### 只为需要的精排器付费

`Reranker` Protocol 新增 `uses_tokens: bool` 类属性。`LexicalReranker` 为 `True`，`NoopReranker` 与 `CrossEncoderReranker` 为 `False`——cross-encoder 需要的是原文，分词结果对它是错误的输入。

pipeline 仅在 `reranker.uses_tokens` 为真时执行查库。

### 失败降级

`_stored_tokens()` 捕获 `SQLAlchemyError` 后返回全 `None` 并记警告，退回实时分词。精排是质量特性，元数据库抖动不应使整个检索失败。

### 回填

新增 `kbsvc backfill-analyzed`，keyset 分页遍历，默认只处理空值，`--force` 用于重算全部。只写元数据库，不触碰 Qdrant 与 Tantivy。

线上 22,345 段耗时 42 秒；重跑返回 0，幂等。

**修改 `lexical/tokenizer.py` 后必须执行 `--force`**：存量值只对产生它的分词器有效。

## 选择该方案的原因

- 打分完全等价，在没有评测集的前提下这是可验证性的关键；
- 向量库与倒排索引的体积和查询开销均不受影响；
- 回填是一次纯元数据遍历，不需要重新嵌入（2.7 小时）也不需要重建倒排索引（该路径此前出现过静默失败）；
- 缺值退回机制使部署可分阶段、可中断。

## 被否决的方案

### 写入 Qdrant 与 Tantivy 的 payload

否决原因：两个索引各涨约 50 MB；每次查询多传输并解析约 96 KB JSON，抵消部分收益；回填需要 Qdrant `set_payload` 就地更新加上重建 Tantivy 索引，而后者是此前出现过静默失败的路径。

### 进程内 LRU 缓存，不落盘

否决原因：冷路径与现状完全相同，收益取决于查询间候选集的重合度，对本语料无法预先估计。可作为试探手段，但不是稳定方案。

### 不物化 token，改为对查询词做子串扫描

实测快 19.9 倍（对比预计算方案的 7.3 倍），且零存储。

否决原因：**会改变打分**。Latin 词边界会产生子串误匹配（`hybrid` 命中 `hybridization`），且 `earliness` 的分母从 token 下标变为字符下标，两者语义不同。在没有评测集的情况下无法验证排序变化的好坏。

### 只存一元组，查询时重建二元组

存储可从 3.5 倍降到 1.6 倍，并可能落在 Postgres 2 KB 的 TOAST 阈值以内，省掉约 6 ms 的解压开销。

否决原因：实测重建结果与原分词**不一致**——二元组不能跨标点边界，而拼接后的一元序列丢失了分段信息；要修正需额外存储分段边界。且重建 CPU（5.18 ms）反而比直接 `split()`（3.37 ms）更慢。它会破坏「打分完全等价」这一选择本方案的前提。

## 后果

### 正面后果

实测 A/B（容器内同进程，40 个候选，均值 599 字符）：

| | 耗时 |
|---|---|
| 实时分词 | 26.09 ms |
| 预计算（查库 9.61 + 打分 5.22） | **14.83 ms** |

分词本身从 26.09 ms 降至 5.22 ms（5 倍），净省约 11 ms。

### 负面后果

- **`chunk` 表从 47 MB 增至 118 MB**（+71 MB）。`analyzed` 均值 2121 字节，是原文的 3.5 倍，超过 Postgres 2 KB 的 TOAST 阈值。已 VACUUM 确认无死元组，118 MB 为稳态。
- **查库耗时 9.61 ms**，其中约 6 ms 是 TOAST 的取出与解压（只查 id 为 1.99 ms，查 `analyzed` 为 8.10 ms）。`session_scope()` 本身仅 0.25 ms。
- **检索路径开始依赖 PostgreSQL 读 chunk 表**。此前检索完全不碰元数据库。已通过降级缓解，但依赖关系是新增的。
- 分词器变更后必须记得 `--force` 回填，否则存量值静默失效。

上述前两项在决策时曾被低估：原估计为表增量约 18 MB、查库 2–5 ms。实测分别为 71 MB 与 9.61 ms。差异来源均为 TOAST，决策结论不变（净收益仍为正），但代价高于预期。

## 验证要求

- 预计算与实时分词在真实语料上逐条同分；
- 部分回填（含空值与非空值混合）打分正确；
- ingest 写入的 `analyzed` 等于 `analyze(text)`；
- 回填幂等，重跑返回 0。

以上四项均已覆盖为单元测试。

## 后续决策

以下事项不属于本 ADR，若实施需要应另建 ADR：

- 若 71 MB 成为问题，为 `analyzed` 设置 `SET STORAGE EXTERNAL`（免解压、增磁盘）或回退该列（回退安全：删列即可，精排自动退回实时分词）；
- 改变 `lexical/tokenizer.py` 的分词策略；
- 引入检索质量评测集后，重新评估被否决的子串扫描方案。
