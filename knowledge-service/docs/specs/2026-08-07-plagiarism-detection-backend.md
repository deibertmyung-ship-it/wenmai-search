# 规格：抄袭检测后端能力

- 状态：Ready for implementation
- 日期：2026-08-07
- 适用模块：`knowledge-service`
- 约束来源：[ADR-0001](../adr/0001-selectively-port-noplag-into-kbsvc.md)
- 文件级实施方案：[2026-08-07-noplag-backend-api-implementation-plan.md](../plans/2026-08-07-noplag-backend-api-implementation-plan.md)

本规格描述**做什么**与**如何验收**。文件清单、移植逐项对照和分阶段顺序见上述实施方案；架构约束与被否决的方案见 ADR-0001。三者冲突时，以 ADR-0001 为准。

## Problem Statement

使用者已经把大量文档灌进了知识库，但没有办法回答一个基本问题：**「我手上这篇东西，和库里已有的内容有多少是重复的？」**

今天只能靠检索去猜——把可疑段落粘进搜索框，看看有没有相似结果。这条路有三个走不通的地方：

- 检索返回的是「语义相关」，不是「文字重复」。改写过的段落照样命中，原样抄的段落如果用词冷僻反而排在后面；
- 检索一次只能看一段。一篇几万字的稿子要人工切成几十次查询，且无法回答「整篇的重复率是多少」；
- 检索结果给不出**可核对的证据**：哪一段、对应到哪本书的哪个字符区间、重复了多长。

对于古籍语料这个场景，这个缺口尤其明显：同一部经典有大量转引、节录和汇编本，判断一份新材料是原创整理还是整段搬运，目前完全依赖人工通读。

## Solution

在 `kbsvc` 内提供 API-first、自托管的**原文及近原文复用检测**：提交一段文本或指定一篇已有文档，系统异步地把它与**调用方在本租户内当前可见的知识库文档**逐段比对，返回带字符区间的可核对证据。

从使用者角度，一次完整的交互是：

1. 提交待检内容（直接给文本，或指名一篇已入库文档），立即拿到任务 ID；
2. 订阅进度，实时看到「排队 → 分块 → 召回 → 对齐 → 落库 → 完成」；
3. 完成后取报告：命中了哪些来源文档、每处命中在待检文本和来源文档中的字符区间、命中长度与分数、以及一小段可读的预览；
4. 结果**可审计**：报告固化了比对时刻的语料快照与来源版本，事后文档更新不会让旧报告悄悄变样。

明确不承诺的能力：深度改写、同义替换、翻译抄袭、公网来源。首期只做**可解释的原文与近原文复用**。

## User Stories

### 提交检测

1. 作为 API 调用方，我想直接提交一段文本做检测，以便在内容尚未入库时就能查重。
2. 作为 API 调用方，我想指定一篇已入库文档做检测，以便复查已有材料而不必重新上传。
3. 作为 API 调用方，我想在提交后立刻拿到任务 ID 和 202 响应，以便不必等待长耗时计算完成。
4. 作为 API 调用方，我想在提交超长文本时得到明确的「输入过大」错误而非超时，以便知道该拆分再试。
5. 作为 API 调用方，我想让系统自动推断语言，以便不必为每次请求指定。
6. 作为 API 调用方，我想在检测文档时自动排除该文档自身的**所有历史版本**，以便旧版本不会形成自匹配噪声。
7. 作为 API 调用方，我想带幂等键提交，以便网络重试不会产生两个任务。
8. 作为 API 调用方，我想在同一幂等键配上不同请求内容时收到冲突错误，以便及早发现客户端 bug 而不是拿到错误的旧结果。
9. 作为 API 调用方，我不希望能够按请求覆盖算法参数，以便所有结果在同一套可比的口径下产生。

### 语料就绪

10. 作为 API 调用方，我想在语料尚未构建完成时收到「语料未就绪」而非静默地拿到不完整结果，以便不会把「没查到」误解为「没有重复」。
11. 作为 API 调用方，我想在可见语料为空时收到明确的「语料为空」错误，以便区分「无重复」和「无可比对内容」。
12. 作为 API 调用方，我想查询当前可见语料的就绪状态，以便在提交前判断能否得到有效结果。
13. 作为运维，我想让新入库文档自动进入抄袭语料，以便无需为每篇新文档手工触发。
14. 作为运维，我想让语料构建失败**不影响**普通入库的成功状态，以便抄袭功能的问题不会阻塞知识库主流程。

### 查看进度

15. 作为 API 调用方，我想订阅任务进度事件流，以便向终端用户展示实时状态。
16. 作为 API 调用方，我想在订阅时先收到已经发生过的事件，以便晚订阅也不丢失前面的阶段。
17. 作为 API 调用方，我想在断线重连时凭上次收到的事件 ID 续传，以便既不丢事件也不重复处理。
18. 作为 API 调用方，我想在订阅后短时间内一定收到点什么（当前状态、事件或心跳），以便区分「还在算」和「连接坏了」。
19. 作为 API 调用方，我想在任务进入终态后事件流正常关闭，以便客户端能干净地结束循环。
20. 作为 API 调用方，我想让关闭事件流**不会**取消正在跑的任务，以便可以随时断开再回来看。
21. 作为安全负责人，我想让进度事件里不出现待检全文、来源全文、密钥或异常堆栈，以便事件流不成为数据泄漏面。

### 取结果

22. 作为 API 调用方，我想拿到每处命中在待检文本与来源文档中的**字符区间**，以便在自己的界面上高亮标注。
23. 作为 API 调用方，我想拿到来源的文档 ID、版本和内容哈希，以便结论可追溯、可复核。
24. 作为 API 调用方，我想拿到一小段命中预览，以便不必回查原文就能快速判断。
25. 作为 API 调用方，我想让报告只给预览而非来源全文，以便来源正文的读取仍然走既有的受权限保护的文档接口。
26. 作为 API 调用方，我想在多个来源命中同一段待检文本时看到正确拆分的来源列表，以便判断是汇编还是单一来源搬运。
27. 作为 API 调用方，我想让同样的输入、同样的快照、同样的算法配置产生**确定的**结果，以便结果可复现、可对账。
28. 作为 API 调用方，我想在执行预算耗尽时拿到部分结果并被**明确告知不完整**（含已检/总分块数与原因），以便不会把部分结果当作「无抄袭」结论。

### 权限与隔离

29. 作为租户管理员，我想让检测只与本租户内的文档比对，以便不同租户的数据互不可见。
30. 作为租户管理员，我想让检测遵循既有的 ACL 语义，以便调用方看不到自己本来无权访问的内容。
31. 作为 API 调用方，我想让任务默认只有创建它的凭据可以查询、订阅、取报告、取消和删除，以便同租户的其他调用方看不到我的检测。
32. 作为安全负责人，我想让访问不属于自己的任务统一表现为「不存在」，以便无法通过响应差异探测任务 ID 是否存在。
33. 作为安全负责人，我想在读取报告时**重新**校验来源的当前可见性，并在可见性已变化时拒绝返回旧报告，以便权限收回后历史报告不成为泄漏渠道。

### 任务生命周期

34. 作为 API 调用方，我想取消一个排队中的任务并立刻清除其敏感内容，以便误提交能马上撤回。
35. 作为 API 调用方，我想取消一个运行中的任务，并接受它是协作式终止（先标记、后清理），以便不会强杀导致数据处于半截状态。
36. 作为 API 调用方，我想删除一个已完成的任务及其原文与报告，以便控制数据留存。
37. 作为运维，我想让待检原文、报告和事件按保留期自动清理，以便不必手工维护数据增长。

### 运行与运维

38. 作为运维，我想让检测由**独立进程**执行，以便 CPU 密集的对齐不会阻塞解析、嵌入或索引写入。
39. 作为运维，我想在 worker 崩溃后由另一个实例接管过期任务，以便不需要人工重启捞回。
40. 作为运维，我想让两个 worker 不会领取同一个任务，以便不产生重复结果。
41. 作为运维，我想让任务重试不产生重复的来源与命中记录，以便报告在重试后依然正确。
42. 作为运维，我想优先构建语料投影再执行检测，以便新入库文档不会长期处于不可比对状态。
43. 作为运维，我想用命令行初始化 schema、回填历史语料、重建投影、查看状态和执行清理，以便完整的生命周期都有可操作入口。
44. 作为运维，我想让回填和重建只**登记任务**而不在命令行进程里直接算，以便长耗时工作可中断、可恢复、可观察。
45. 作为运维，我想在算法配置变化后被明确要求重建，以便不会拿新配置去查旧投影产生错误结果。
46. 作为运维，我想通过就绪检查看到 schema、worker 心跳、算法哈希与语料覆盖率，以便判断该功能是否真的可用。
47. 作为运维，我想让功能默认关闭，并且「对外开放」与「后台建索引」是两个独立开关，以便先把历史语料建好再开放接口。
48. 作为运维，我想在非 PostgreSQL 环境下应用仍能正常启动、相关接口返回明确的不可用错误，以便本地 SQLite 开发不被阻断。
49. 作为运维，我想让错误信息不暗示 SQLite 可用，以便不会误导使用者去尝试不受支持的配置。

### 移植与合规

50. 作为维护者，我想让移植来的算法在固定语料上产生与上游一致的结果，以便适配改动没有悄悄改变算法语义。
51. 作为维护者，我想让每个移植文件都注明上游出处、固定提交与「已修改」声明，以便将来能对照上游升级。
52. 作为维护者，我想保存上游许可证全文并在仓库根记录第三方归属，以便许可合规可审计。

## Implementation Decisions

### 模块边界

新建深模块 `kbsvc.plagiarism`。HTTP 路由、CLI 与入库 worker **只穿过一个稳定 seam**：`PlagiarismService`。

`PlagiarismService` 对外提供：创建文本检测、创建文档检测、查询单个检测、分页列出检测、读取报告、删除检测、查询语料就绪状态。

worker 侧使用两个内部接口：`ProjectionBuilder`（构建语料投影）与 `CheckRunner`（执行检测）。

强制约束：

- 路由不得直接调用指纹、候选检索或 SQL；
- 算法代码不得创建数据库连接、读取环境变量、接触 HTTP 对象或自行提交事务；
- 模块只导出 service 与稳定的请求/结果类型，不导出数据库模型与算法内部函数。

### 数据访问

全部改为**同步 SQLAlchemy**，复用现有 engine、Session 与事务。不在同一进程引入第二套异步 engine 或连接池。

抄袭检测**只支持 PostgreSQL**，依赖 `BIGINT[]`、数组 overlap 查询与 GIN 索引。候选查询以 ARRAY overlap + GIN 为唯一首期实现，**不提供 Python 全表扫描 fallback**——有 fallback 就会在生产上悄悄退化成不可用的慢查询。

SQLite profile 不加载抄袭相关模型、不建表，相关接口返回 503。为此抄袭模型使用独立的 declarative base，与主 schema 分离。

### 数据模型

新增一组 `plag_*` 派生表，覆盖：语料投影、投影分块与指纹、指纹 document frequency、语料构建任务、检测任务、命中来源、命中片段、进度事件、worker 心跳。

关键决定：

- 这些表是**可重建的检测投影，不是文档事实来源**。文档、版本、ACL、原始文件与知识检索索引仍由既有模块拥有，`plag_*` 只做受控引用；
- 投影带 active 时间区间，用于按快照时刻过滤；
- 进度事件使用单调递增整数 ID，直接作为 SSE 的事件 ID；
- 幂等键在「租户 + 创建者凭据 + 路由 + 幂等键」上唯一。

首期沿用项目现有的建表方式（见 [ADR-0004](../adr/0004-additive-column-migration-without-a-framework.md)），正式 migration 工具另立 ADR。

### 快照语义

创建检测时，在**同一个事务内**完成：计算调用方当前可见的文档集合 → 校验这些文档都有匹配当前算法哈希的 active 投影 → 记录数据库时刻与算法哈希 → 创建任务并写入首个事件。

语料为空返回「语料为空」，投影不完整返回「语料未就绪」。**不得对不完整语料静默执行检测。**

候选查询必须**重复**校验租户、ACL、快照时间区间与算法哈希，不能只依赖创建时的检查——创建与执行之间存在时间差。

### 并发与幂等

- 请求摘要包含模式、文本哈希或文档版本、以及调用路由；同键同摘要返回原任务，同键不同摘要返回冲突；
- 使用 advisory transaction lock 把「统计活动任务数并创建」串行化，锁的 key 由租户与创建者凭据稳定计算；
- 每个凭据默认最多 2 个活动任务，超限返回 429；
- 任务领取使用 `FOR UPDATE SKIP LOCKED` 加租约，配合指数退避与最大尝试次数。

### 任务状态

固定为：`pending` / `running` / `completed` / `completed_partial` / `failed` / `cancel_requested` / `cancelled`。

状态迁移集中定义，非法迁移抛领域错误。路由与 worker 都不能直接写任意状态。

时间预算耗尽时保留已发现结果并以 `completed_partial` 结束，报告必须携带覆盖原因与已检/总分块数，并明确说明**不可作为完整无抄袭结论**。

取消是协作式的：worker 在分块、候选批次与对齐批次之间检查取消标志，不强杀线程或进程。

### HTTP 契约

在既有 `/v1` 下新增：创建文本检测、创建文档检测、列出检测、查询检测、读取报告、订阅进度、删除检测、查询语料状态。

- 幂等键从 header 读取，不放进 JSON body；
- 创建返回 202；删除终态任务返回 204；删除运行中任务先转入 `cancel_requested` 并返回 202；
- 复用既有 Principal 解析与错误信封；
- 报告只返回来源元数据、字符区间、分数与不超过约 300 字符的预览。

新增错误码及映射：功能关闭/不可用 → 503；语料未就绪、语料为空、幂等冲突、报告可见性已变化 → 409；并发超限 → 429；输入过大 → 413；任务不存在 → 404。

### SSE 契约

事件帧（这是对外契约，客户端据此实现，故在此固化）：

```text
id: <事件的单调递增整数 ID>
event: queued|started|chunking|retrieving|aligning|persisting
     |completed|completed_partial|failed|cancelled|keepalive
data: {"check_id": "...", "status": "...", "progress": 0.0,
       "detail": {...}, "created_at": "..."}
```

规则：

- 未带 `Last-Event-ID` 时从首条事件开始回放；带了则只返回更大的 ID；
- keepalive 不落库，也不占用可恢复的事件 ID；
- **终态事件必须与任务终态在同一数据库事务内提交**，否则会出现「任务已完成但事件流永远等不到终止」；
- 事件表是唯一事实来源，不使用进程内队列保存可靠状态；
- 首期允许短轮询事件表实现等待。

### 执行与部署

抄袭 worker 与既有入库 worker **分进程**部署，不复用既有任务表。不使用 FastAPI 后台任务——服务重启会丢执行，且无法跨进程提供可靠的 SSE。API 的 lifespan 不启动抄袭 worker。

worker 优先处理语料投影任务，再处理检测任务。

普通入库在完成解析与既有索引写入、确定当前版本之后，通过一个极小的适配点登记语料构建任务。该登记在**嵌套事务/savepoint 内**执行，失败只记日志，**不得**把文档版本标记为失败——抄袭是附加能力，不能让它拖垮知识库主流程。

### 配置与发布门禁

新增一组 `KB_PLAG_*` 配置，覆盖：功能开关、算法参数、任务参数、限额、SSE 参数、保留期、并发度。

- 「对外开放」与「后台建索引」是**两个独立开关**，使历史语料可以在接口关闭时先建好；
- 只有影响投影兼容性的参数参与算法配置哈希；哈希变化后新任务只能使用新配置的投影，且在全量重建完成前拒绝创建检测；
- 功能启用后，就绪检查纳入 schema、worker 心跳、算法哈希与语料覆盖率。

### 依赖与合规

不新增异步 SQLAlchemy、SSE broker 或第二套 Web 框架。PostgreSQL 路径继续使用既有 postgres extra。

移植文件逐个注明上游路径、固定提交、上游许可证与「已修改」声明；仓库根新增第三方归属文件并保存上游许可证全文。

## Testing Decisions

### 什么算好测试

**只测外部可观察行为，不测实现细节。** 测试应当描述「使用者能看到什么」，而不是「代码内部怎么组织的」。判据是：重构模块内部结构而不改变对外行为时，测试不应该需要修改。

**唯一的例外是算法基线测试**，它的目的**就是**钉住实现输出——这是一次代码移植，「适配过程没有改变算法语义」是必须被证明的，而这只能在算法层观察。

### 三个 seam

经确认收拢为三个，而非按模块分层：

**Seam 1 — HTTP（复用现有的 API 测试客户端 fixture）**

这是最高的 seam，吸收绝大部分验收项：两种创建模式、分页列表、状态查询、报告内容、删除与取消、SSE 回放与断线续传、租户/ACL/创建者三重隔离的零越权、幂等重放与冲突、全部错误码、功能开关的开与关、读取报告时可见性变化返回冲突。

投影与检测的**可观察行为**在这一层验证（例如「配置哈希变化后旧投影不可用于新任务」表现为创建检测被拒绝），不为它们单独开 seam。

**Seam 2 — worker 排空（复用既有入库 worker 的 `drain()` 测试模式）**

只放无法从 HTTP 稳定观察的进程语义：两个 worker 不领取同一任务、过期租约可被回收、最大重试与退避、协作取消最终清除敏感内容、时间预算产生部分完成、心跳可供就绪判断、重试不产生重复结果。

**Seam 3 — 算法基线（新增，最低层）**

从上游迁移固定输入/输出向量：指纹、滑动分块与字符偏移、区间合并、对齐（完整复制/局部复制/多段复制）。覆盖 Unicode、重复 token、短文本与确定性。这层是移植保真度的证据，实施阶段 1 结束时即应全绿。

### PostgreSQL 策略

经确认：**复用 compose 里已在运行的 postgres**（已映射 5432），测试使用独立的测试库，不引入新的开发依赖。

现有测试套件全跑在 SQLite 上，抄袭部分是首个需要真实 PostgreSQL 的测试集。因此：

- 依赖 PostgreSQL 的用例在数据库不可用时 **skip 并明确报告 skip 原因**，不得静默通过。「没跑」和「跑过了」必须能区分；
- 这一层必须覆盖：GIN overlap 命中、快照时间区间过滤、ACL overlap、`SKIP LOCKED` 领取、advisory lock 串行化、schema 初始化幂等；
- 用查询计划断言代表性候选查询确实走 GIN 索引——这是「不提供 fallback」这一决定的配套证据，否则索引失效会表现为悄悄变慢而非失败。

### 既有测试的回归责任

抄袭功能默认关闭，因此必须证明它在关闭态下**完全没有副作用**：现有检索、入库、MCP 与 API 行为不变；入库路径在登记失败时不污染文档状态；API 启动不拉起抄袭 worker；非 PostgreSQL 环境应用可正常启动。

### 现有可参照的写法

- HTTP seam 的既有范例是现有的 API 与 MCP 测试，使用 session 级的测试客户端 fixture；
- worker seam 的既有范例是入库测试中「注册 → `drain()` → 断言落库状态」的模式，以及既有的两 worker 竞争与租约过期用例——抄袭 worker 的对应用例应当照此写；
- 纯函数层的既有范例是检索单元测试。

## Out of Scope

- **前端与 MCP 工具**：本规格只交付后端 HTTP 能力，不含 Web 界面与 MCP tool 暴露；
- **公网语料**：只与本租户内已索引文档比对；
- **语义改写、同义替换与跨语言抄袭检测**：首期只做原文与近原文复用；
- **SQLite 支持**：明确不做，相关接口在非 PostgreSQL 下返回不可用；
- **远程语料管理 API**：语料的初始化、回填、重建、清理只提供命令行入口；
- **`LISTEN/NOTIFY`**：首期用短轮询事件表，事件表始终是可靠来源；
- **正式 schema migration 框架**：沿用现有建表方式；
- **租户管理员查看全部检测任务的角色模型**：首期任务只对创建者凭据可见；
- **统计聚合、标题修改、文件上传检测、远程全量重建**；
- **按请求覆盖算法参数**。

以上任何一项若在实施中变得必要，**停止扩展并新建 ADR**，不在本次实现中临时发挥。

## Further Notes

### 与既有决策的关系

本规格完全落在 ADR-0001 的约束内。三处与其他 ADR 的接触点：

- 建表方式沿用 [ADR-0004](../adr/0004-additive-column-migration-without-a-framework.md) 的判断（不引入迁移框架）。ADR-0001 与 ADR-0004 都把「引入正式 migration 工具」列为后续决策，应合并考虑；
- 抄袭 worker 与入库 worker 分进程，与 `docs/superpowers/specs/2026-08-06-lexical-writer-worker-scaling-design.md` 中「词法写入独立进程」的方向一致，但两者互不依赖，可各自推进；
- 检测报告只返回预览、来源正文仍走既有文档接口，与既有的 ACL 边界保持一致，不新增读取路径。

### 验收门槛

功能对外开放前必须同时满足：

- 完整复制与局部复制可返回正确来源与字符区间，无关文本不产生明显长段误报；
- 多来源拼接正确拆分并去重查询侧覆盖区间；
- 同一文档的历史版本不会成为来源；
- 租户、ACL 与任务所有权测试零越权；
- 同输入、同快照、同算法哈希结果确定；
- worker 重启、租约过期与重试不产生重复结果；
- SSE 断线重连不丢终止事件；
- 时间预算耗尽明确产生部分完成；
- 移植前后在固定语料上的指纹、候选、命中区间与报告达到既定迁移基线；
- 创建请求 P95 低于 500 ms；订阅后 2 秒内有响应；不超过 100,000 字符的标准验收集在 60 秒预算内达标。

### 发布顺序

建表与索引 → 启动抄袭 worker → 开启后台建索引并完成历史回填 → 重建 DF 并执行统计分析 →
确认当前算法哈希覆盖率 100% → **通过下方验收** → 开启对外开关。

闸门是**验收结果**，不是「必须由人敲一次命令」。前者能被检查和复现，后者只是一道仪式。
`KB_PLAG_ENABLED` 默认仍为 `false`——新部署没有语料，开着毫无意义——但一旦某个部署跑完
上述顺序并通过验收，即可开启，不需要额外的人工确认环节。

### 本部署的验收记录（2026-08-08）

语料：201 部古籍，232,960 个投影分块，320 万指纹，DF 表 2,099,459 条。

| 项 | 目标 | 实测 |
|---|---|---|
| 创建请求 P95 | < 500 ms | **164 ms**（中位 88 ms） |
| SSE 首字节 | < 2 s | **76 ms**（中位 50 ms） |
| 100,000 字符 | 60 s 预算内 | **32.6 s**，1498/1498 分块查完 |
| 语料覆盖率 | 100% | 201/201，0 失败 |
| GIN 索引 | 真实数据量下命中 | Bitmap Index Scan，33 ms |
| 逐字复用可找回 | 是 | 找回原书，score 1.000 |
| 无关文本零误报 | 是 | 现代白话、原创文言均 0 命中 |

验收过程中修掉三个只有真实语料才暴露的缺陷，均已补回归测试：

1. **格式行误报**——300 个连字符被报成四部书各命中 100%。分隔线与语料里每条分隔线
   逐字相同，是真实的 verbatim 匹配也是毫无意义的匹配。守卫加在**片段级**（只加分块级
   不够：嵌在正文里的分隔线所在分块整体「多数为文字」，能通过分块检查）。
2. **创建路径的 N+1**——`_visible_document_ids` 逐个 `session.get(Document)`，201 篇文档
   下 P95 815 ms，超出目标。只在 ACL 非空时触发，也就是所有真实调用方。修掉后 164 ms。
3. **compose 只透传了 2 个 `KB_PLAG_*`**——`.env` 由 compose 读取用于插值，并不挂进容器，
   未在 `environment:` 里点名的变量对应用不可见，应用于是静默用代码默认值。
   `.env.example` 记了 25 个，全部补齐。

`KB_PLAG_INDEXING_ENABLED` 与 `KB_PLAG_ENABLED` 仍是两个独立开关：前者让语料可以在
接口对外关闭时先建好，这一点不变。

### 一处需要留意的既有事实

知识库当前的删除是软删：文档标记删除后，对象存储中的原始文件**不会**被回收（已观察到实例：202 个对象对应 201 篇在册文档）。抄袭语料投影按当前可见文档集合构建，因此软删文档会退出语料——但其原始文件仍在。这不影响本规格的正确性，但在讨论数据保留时应把两者分开看：抄袭模块的保留期只管 `plag_*` 数据，不改变对象存储的既有行为。
